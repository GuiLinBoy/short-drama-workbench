# 画布审核工作流

沿用各作品已经确定的审核节点及有效批准，制作范围以用户当前指示、实际请求和费用授权为准。2026-11-08的开发暂停是历史记录，不作为后续作品的默认限制；开发、离线检查和隔离样例本身也不构成新增生成或消费授权。

## 用户怎么用

### 用户明确委托审核时

默认沿用用户亲自审核；用户在当前作品明确说“不再审核、交由执行者完成”时，按其实际授权切换为总导演代审，不反复要求用户点击。授权必须保存本作品工作区ID、绝对目录、原话、范围及 `delegatedReview: true`，不得套用到其他作品。

`canvas_review.py --project <作品> delegate --authorization <作品内授权.json> --assessment <作品内实际检查.json>` 保留同一审核项和完整历史，单独记录 `DELEGATED_DIRECTOR_REVIEW`、授权及证据指纹。检查文件绑定当前审核ID、fingerprint、head及实际证据SHA，逐项填写结果和具体判断；缺项、证据变化、依赖未通过、失败或未完成检查均不能采用。HTTP用户操作仍记 `CANVAS_USER_ACTION`。审核方式变化不豁免H3内部复核、声音收尾、真实听看、预算流水、就绪或未知任务检查，不自动授权公开发布。

下文“待用户通过/验收”描述默认流程；明确委托范围内由总导演执行同等检查并留下真实代审记录，不生成虚假的用户批准。仅有普通导演 `approved` 字段仍不构成代审。

### 同一素材原位返工（2026-11-15）

最终 `video_prompt` 可用 `storyboard: "作品内分镜.md"` 将内部文字分镜随实际请求一起送审；该文件纳入同一版本指纹，修改后原确认失效。不另建分镜审核节点；方案与实际媒体依赖仍须满足。未提供合并分镜的旧包沿用原依赖检查。

- 同一人物、场景或视频片段只保留一个可见节点、一个当前版本。要求修改后撤下当前失败图/视频；准备新的提示词后在原节点展示，生成新结果后原位替换。旧文件和审核记录留在历史中，不新建“修改输入”“修正版”等独立节点。
- 返工送审沿用原素材 `subject`，审核包、提示词、请求和输出文件用新版本。确需修复历史上误建的素材编号时，可在作品 `创作画布.json` 的 `assetAliases` 显式映射到原素材，例如 `{"S00002":"S00001"}`；这只是展示归并，不篡改历史，也不把真实服装/场景变体按 `source_asset_id` 合并。
- 同一素材的局部改图可在新 `image_prompt` 包添加 `editSource: {reviewId, recordSha256, path, sha256}`，绑定历史 `image` 包记录及原图字节，只允许真实 `/images/edits` 请求使用。该原图是待修输入，不是已采用素材，不再为它创建审核节点或要求用户先通过失败图。它不放入 `dependsOn`；方案等正常依赖照常保留，其余参考素材仍按原规则审核。
- 新提示词仍待用户通过，新的图片结果仍待用户验收；历史原图不会因此获批，预算、attempt 和受控生成入口不变。
- 片段开场构图图可用该片段ID（如 `EP001/Clip00001`）作为 `image_prompt` / `image` 的 subject，直接归入已有视频节点；若生图工具需要后台素材登记，可在 `assetAliases` 显式把该素材ID映射到已登记片段ID。仅改变画布展示归属，不修改图片审核类型、依赖、生成工具或授权。新的图片提示词会撤下该节点旧视频，图生成后原位显示图片，后续视频提示词仍单独按原节点审核。
- 用户选择独立保留构图图时，在作品 `创作画布.json` 设置 `clipReferenceImages`，如 `{"EP001/Clip00001":"S00003"}`。该素材固定显示为图片节点并连接对应视频；图片和视频各保留一个当前版本，沿用原审核 ID、subject 和实际依赖。移除该素材原来的视频节点别名；其他素材的修订归并不变。此设置不修改审核状态，也不追加确认。
- 若旧视频已经按用户要求撤下，拆分前同步记录 `withdrawnVideoThrough`，如 `{"EP001/Clip00002":"EP001-Clip00002-video-result-v004"}`，绑定已存在的该片段视频审核项。它及更早的视频提示词/结果收进历史，原视频节点显示“待准备新版提示词”；新提示词送审后仍回到同一视频节点。仅生成另一张参考图不自动撤下已采用视频。

打开本机画布，进入「待你确认」。创作画布右上角也有入口；节点详情的「查看本项用户审核」按送审包的 `subject` 定位。

1. 在「待处理」查看未通过、要求修改、暂缓、版本变化的内容；按环节或片段搜索。
2. 右侧查看中文分镜、图片、视频、正式请求的实际提交提示词、参数及参考素材。
3. 勾选一个或多个项目，选择「通过所选内容」「要求修改」「暂缓」「仅补充意见」。修改和补充意见必填。
4. 在「审核记录」查时间、决定、意见和对应版本。本项详情也有自己的历史。
5. 一批保存完后，点击「本批审核完成，通知总导演」，查看真实排队、投递及接收状态，见 [通知说明](CANVAS_NOTIFICATION.md)。

### 取消暂缓与筛选

在「筛选审核状态」选择「已暂缓」，勾选一项或多项，点击「取消暂缓，恢复待确认」。系统追加取消记录、保留原暂缓和意见，自动切换到待确认状态筛选；不会恢复旧通过状态、放行依赖、恢复制作或取消平台任务。新的取消决定可随下一批通知提交给总导演。内容已变化但仍保留暂缓决定时，也能先查看当前版本再取消；旧页面不能代替新版本操作。

混合选择暂缓与非暂缓项目时不能批量取消；不允许把普通待确认、要求修改或已通过项冒充暂缓来恢复。重复请求不会重复记记录。

「选择待确认项」只自动选择当前范围内、依赖齐备的待确认项目，不默认选入已暂缓、要求修改、需重审或已通过项。切换筛选后，仍被勾选但不可见的项目会阻止所有审核提交；可用「恢复筛选并查看所选」定位回来，或清空选择，未保存意见保留。右侧详情始终来自当前可见范围，勾选时定位对应项目。

单项保存只新增本地审核记录，不调用模型、不生成、不重试、不唤醒会话；整批通知另由用户点击入队、活动调度投递。补充意见不改变上一项决定。通过后修改内容、参数、正式请求或上游内容会使旧确认失效；有未通过的依赖不能批准。页面选中后若内容或审核记录发生变化，必须重新查看、选择。

已有 `assets.json` / `clips.json` 的导演 `approved` 不会自动转成用户确认。没有送审包时为空列表；不向历史作品自动补写批准记录。

## 六个确认环节

角色首次开口的视频通过后，主执行者同轮执行 [音色收尾](VOICE_CLOSEOUT.md)，将真实提取并登记的音色送到唯一 `audio` 节点，依赖已通过来源视频。画布即时展示收尾状态，视频通过不自动批准声音或启动生成。已有同一声音文件的有效确认复用；声音节点通过后同轮同步采用。后续同角色视频依赖该已通过声音项，并在实际请求中附加同一音频。

| 环节 | kind | 内容 |
|---|---|---|
| 1 | `plan` | 剧本、风格、制作规格、预算/次数/返工范围、硬要求与导演可调整项 |
| 2 | `storyboard` / `image_prompt` | 分镜内容与提示词、图片实际提交提示词 |
| 3 | `image` / 可选 `audio` | 生成图片、定妆/场景选择、声音样本 |
| 4 | `video_prompt` | 每段正式视频提示词、实际参考图/音频、参数和本次 attempt |
| 5 | `video` | 每段实际视频，包括试生成、定稿及返工的新版本 |
| 6 | `final` | 完整成片 |

`exception` 用于额外费用、新渠道、未知任务重发等独立申请。例外确认仅留证，不自动改预算、上限、未知重发规则或就绪文件。现有专门授权仍必须核对。公开发布另行授权。

## 总导演怎么送审

### 面向用户的简洁展示（2026-11-08）

用户主要确认创作内容、实际效果及费用边界。六个环节统一采用“需要你决定的事项 → 实际提示词/剧本/预算 → 图片、声音或视频 → 按需展开的专业附件”。参数、路径、校验值、执行证据、岗位报告和版本依赖折叠备查，原始送审文件、版本指纹、审核记录及批准条件保持不变。

- `summary` 尽量控制在80—160字，直接写本次用途、需要用户确认什么，以及影响效果的偏差；不要堆放SHA、任务路径、exitCode或内部恢复记录。
- 方案审核突出剧情、风格、时长、规格、预算金额/次数/返工；分镜与提示词突出镜头内容和实际中文提示词；图片/声音突出实际效果与是否采用；视频提示词突出动作、对白、镜头和参考素材；逐段视频突出实际效果、口型和衔接；成片突出完整观感和交付决定，公开发布仍另行授权。
- 图片/视频结果直接关联对应正式提示词送审项，画布在结果页显示关联请求的原文及审核状态。没有正式请求时，不从技术报告猜写提示词；缺失会提示补充。关联版本变化时不能冒充已批准原文。
- 人物朝向等有意义的效果偏差、额外费用、渠道/模型/范围变更必须在可见的摘要或独立申请里明确，不得仅埋在折叠技术报告中。纯技术附件不要求用户逐条背书，专业核对由总导演及岗位负责。
- 剧本、预算、分镜和提示词文本以清晰命名的独立附件提供，避免将唯一的创作内容只写入执行证据。专业报告仍完整保留；本展示调整不代替创作或费用批准。

默认由一个主执行者按五岗职责检查并整理送审包，用户明确要求协作时才另行委派。自然语言正文使用中文。[片段衔接](SHOT_CONTEXT.md) 与 [音色收尾](VOICE_CLOSEOUT.md) 并入已有报告，不增加节点或重复确认。

纯本地入口（不会推理或调用平台）：

```powershell
python -I -X utf8 "D:\ai剧集制作\漫剧\短剧工具\tools\canvas_review.py" --project "作品绝对目录" submit --packet "送审包绝对路径.json"
python -I -X utf8 "D:\ai剧集制作\漫剧\短剧工具\tools\canvas_review.py" --project "作品绝对目录" status
```

CLI **没有批准命令**。`submit` 只登记材料，`status` 只读取审核。送审包放在作品内的提案目录，所列素材必须真实存在，路径必须在作品内；使用版本化文件名，保留旧提示词和媒体。

方案示例：

```json
{
  "id": "EP001-plan",
  "kind": "plan",
  "title": "EP001 制作方案与预算",
  "subject": "EP001",
  "summary": "请确认剧情、风格、硬要求和消费范围。",
  "files": [{"path": "协作/提案/总导演/方案-v001.md", "label": "制作方案"}],
  "dependsOn": []
}
```

图片提示词示例：先用既有 `codex_cli.py image prepare` 离线准备正式请求，再送审。它会自动加入原始提示词和请求内的参考素材，展示正式请求 `prompt`，不会把参数/参考替换隐藏在提交之后。

```json
{
  "id": "C00001-A-image-prompt",
  "kind": "image_prompt",
  "title": "主角视频参考图提示词",
  "subject": "C00001-A",
  "files": [{"path": "提示词/主角-v001.txt", "label": "中文图片提示词"}],
  "dependsOn": ["EP001-plan"],
  "request": "requests/主角-v001.json",
  "generation": {
    "tool": "image",
    "batch": "EP001-参考图",
    "taskDir": "tasks/主角-v001/attempt-001"
  }
}
```

视频提示词用 `video_prompt` / `tool: h3`，依赖已送审的 `plan`、`storyboard` 和所用素材的结果审核项；祖先依赖可传递。每份正式请求中的参考素材必须被上游 `image` / `video` / `audio` 审核项涵盖，当前文件 SHA 也必须与准备请求时一致。上一段尾帧与声音模板应作为相应上游结果包的文件，供用户查看确认。

2026-11-11原样截帧复用：已通过视频内的未编辑PNG帧可随新视频提示词一起展示，不再要求用户批准同一画面的文件格式转换。`video_prompt` 可带 `derivedReferences: [{"path":"参考/原样帧.png","source":"单集制作/EP001/视频.mp4","sourceSha256":"64位源文件SHA256","frameIndex":293}]`。该源视频必须来自当前仍有效、已通过的上游 `video` 审核项；画布使用已登记且指纹匹配的本机FFmpeg重新解码指定零起始帧，逐字节核验PNG，核验失败即拦截。仅支持无裁切、无重绘、无缩放的原样帧；修改后的图片仍按新素材审核。声明及实际图片绑定新提示词版本，源视频撤回或变化会阻断；不写任何用户批准记录，不改变源视频审核。仅复用源媒体批准，后续创作请求仍在原有视频提示词项确认。真实上游尾帧的连续性日志要求保持。

图片、视频或成片结果使用对应 kind，`files` 包含实际交付文件及需要查看的说明、尾帧等，`dependsOn` 指向对应提示词审核项。试生成、定稿和返工结果使用不同 ID。一个批次可包含多个独立片段，每段保持独立审核项。依赖尚未通过的下游会显示阻断原因；同批只批准已经满足依赖的项目。

同一 ID 重送完全相同材料是幂等操作；内容变化会保留旧包并生成新送审版本。`subject` 应与资产ID、完整片段ID（如 `EP001/Clip00001`）或剧集ID一致，供画布节点定位。

## 画布内审核与当前版本

- 创作画布不再展示独立分镜节点；分镜内容在视频详情“分镜与提示词”查看，素材等已有依赖直接连到视频。片段的原分镜记录折叠备查；没有明确视频对应关系的纸面分镜收在作品节点“分镜资料”，不猜测镜头与视频的对应关系。分镜审核项保留原ID并收进相关节点，不改变后台分镜文件或依赖批准条件。
- 已送审的待确认内容直接进入创作画布；即使尚未登记到正式素材或片段清单，也可显示节点、实际提交提示词及送审依赖线。岗位仍须先准备正式请求并送审，画布不会自行编写提示词或猜测依赖。
- 点节点详情的“审核当前版本”，可查看当前提示词、参考素材或实际结果，并通过、要求修改、暂缓或补充意见。“定位待确认”依次定位当前待审节点。
- 同一 `kind + subject` 只展示最后送审的版本；同一完整视频片段的提示词和结果合并到一个视频节点。不同剧集的同号片段、不同的额外授权不会混为一项。新提示词替代旧结果时明确显示尚未生成，不沿用旧视频冒充新版。
- 历史送审包、每次生成文件和审核记录继续保存在原目录；画布只是当前版本视图。旧版本依赖标作“历史版本依赖”，不会自动改成新版依赖或批准新版。
- 节点内决定复用同一审核接口、内容指纹与上一条记录校验。查看过程中版本或状态变化，必须重新读取后再决定；依赖未满足仍不能通过。保存审核不会启动生成。

## 本地记录与执行边界

- 每部作品独立保存在 `协作/审核/记录/`，记录含连续编号、前序摘要和完整校验值；每次提交/批量决定形成一个完整不可覆盖文件。
- 保存送审文本快照、正式请求投影、素材 SHA、意见和时间；不复制大媒体，原媒体必须使用版本化路径保留。页面展示最近300条决定、每项最近100条；更早记录继续留在磁盘。
- 目录写锁防止多进程互相覆盖；旧页面使用内容版本和上一条审核记录做冲突检查。本批一项冲突即全部不写。网络响应丢失后原请求编号重试不会重复记账。
- 只追加审核目录；不改资产/片段清单、不改预算/账本、不覆盖媒体、不操作 Git。
- `codex_cli.py` 对 **image/h3 的 submit --execute** 增加画布前置检查：正式请求、批次及 attempt 必须匹配当前用户通过的版本和全部依赖。此检查在读取凭据和访问平台之前；现有预算、就绪指纹、计数和未知重试限制继续执行，不能被画布通过代替。新增审核模块也纳入就绪指纹。
- 这是本机协作协议，不是防止任意本地程序修改文件的 OS 安全沙箱。历史直接运行底层脚本不受这层入口校验；岗位应继续使用统一 `codex_cli.py` 入口。
- 整批通知由活动调度适配器读取文件队列并使用现有会话工具投递；没有脱离会话的常驻投递。当前投递未启用，导演读取通知也不代表恢复制作。TTS、本地后期和公开发布没有新增自动执行或自动授权。

HTTP提供 `POST /api/reviews` 保存决定、`POST /api/review-notifications` 入队整批通知。只能向已发现作品提交指定格式，不接收文件路径、收件会话ID或执行命令；本机精确同源、会话随机令牌及请求长度检查保护写入。其他写方法拒绝。请求/文件错误均停止批准，不当作通过。
