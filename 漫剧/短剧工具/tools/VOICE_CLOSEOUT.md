# 首次开口后的音色收尾

2026-11-15 用户要求，适用于本工作区每部剧及以后新建作品。来源为现行共享规范，不从旧作品复制人物声线、授权、样本或例外。

## 触发与完成条件

角色第一次实际开口的视频在画布通过后，主执行者必须在处理该次确认的同一轮完成声音收尾。先同步真实采用视频与 SHA，再从该已通过结果提取干净声音，核对并经 `pipeline_state.py --role 摄影 add-voice` 登记，提交 `kind: audio`、`subject: 角色编号` 的声音样本到画布。声音审核项依赖真实来源视频的结果审核项。每个角色只保留一份当前音色节点；不能以“后续待补”代替已可执行的提取、登记和送审。

区分两种状态：

- **制作收尾已完成、等待试听**：音频存在、登记及文件指纹对应、实际来源已通过、声音节点已送审且可确认。允许继续不依赖此人物音色的工作，不能生成该人物后续对白。
- **音色采用完成**：该声音节点实际通过，主执行者在同轮核对文件并将登记同步为 `approved`、更新本作品声音引用映射。已有同一文件的有效确认直接复用，不重复建节点或索取同一批准。

首次台词过短或夹杂其他声音时，仍须保留真实样本并明确限制，不以补静音、循环台词凑时长。短样本由实际试听及现有内部复核判断；需要改用后续较长台词、后期配音或付费定音时，先把具体取舍放回既有审核流程。没有新方案授权不能放行另一个“首次定音”请求。不能借此要求重新确认已通过视频。

## 自动检查入口

```powershell
python -I -X utf8 tools/voice_lifecycle.py --project <作品绝对目录>
python -I -X utf8 tools/voice_lifecycle.py --project <作品绝对目录> --require prepared
python -I -X utf8 tools/voice_lifecycle.py --project <作品绝对目录> --require confirmed
```

纯本地只读；不生成媒体、不写批准、不调用平台。第二条核对提取、登记、送审是否收尾（待试听可保留）；第三条要求音色已实际确认并同步采用。失败返回非零及具体人物、来源和待办，不产生“技术审核”用户节点。

`pipeline_state.py` 的视频状态/文件更新和音色更新返回 `voice_closeout`；`codex_workflow.py status`、项目校验及画布实时显示相同收尾结果。视频批准和声音收尾是两个事实，避免“必须先有已通过音色才能批准定音视频”的循环。计划校验提示未完成事项，合成阶段把未完成音色收尾作为错误。

画布以真正的结果审核为触发证据，即使视频清单尚未同步也会显示待办。声音来源使用实际请求中的说话人；出现在画面但没有对白的人不会被误判为首次开口。缺请求、缺人物绑定、来源失效或文件不一致时如实阻断，不能猜测已完成。

## 后续视频提交

共享 H3 执行检查及提交入口执行以下规则，不以缺配置为由跳过：

1. 已通过首次说话视频而尚未完成提取、登记、送审时，先完成本地收尾；不继续付费提交。
2. 有对白时，必须附加全部且仅本段说话人的已通过音色；登记、声音审核、角色、路径和 SHA 必须一致。实际请求必须为 `reference_audio`，音频编号须在人物定义和逐句对白中绑定。
3. 首次定音仅允许尚无已通过说话视频且尚无音色登记的角色，并仍绑定精确请求、批次、attempt、时长、分辨率和既有用户授权。把第二段重新登记为首次定音不能绕过声音基准。
4. 严格首尾帧不能携带音频参考时，报告模式冲突并调整现有方案；不能自动删除音色参考、改静音或声称已经固定。
5. 新剧不继承旧剧具体声音或例外。已批准的历史视频不因此失去批准；新制作按现行检查推进。实际音色一致性仍须逐段听辨，检查文件不能替代听音。
6. 用户明确不采用尚未采用的候选声音，并要求按文字描述重生成原定音片段时，可登记精确的 `revoiceRequests`。保留原视频批准及声音否定记录，核对同一人物、原视频、样本文件与否定记录；新授权绑定请求 SHA、批次、attempt、时长和分辨率，随声音方案一并留证。此请求只允许普通图片与原生对白，不能混入旧声音或视频参考，不能标成首次定音，也不放宽其他人物的收尾、预算及审核。只适用于该次请求，结果通过后重新完成声音收尾。

规则和代码的变更使旧执行复核、运行指纹需要按现有流程重新核对；不自动增加预算或开启生成。
