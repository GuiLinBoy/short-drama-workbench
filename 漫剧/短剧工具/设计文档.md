## 1. 背景与目标

`novel-to-video` 技能把"小说 → 漫剧成片"拆成 7 个阶段（ingest → design → storyboard → prompts → assets → clips → assemble），原设计由**一个 Agent** 从头跑到尾。这样做有三个问题：

- 单个 Agent 的上下文越跑越长，长篇项目容易忘掉早期设定；
- 各阶段的专业要求不同（编剧、美术、视频、剪辑），混在一个身份里，提示词会互相干扰；
- 很难看清整体进度，也不方便中途人工介入。

**目标**：在 nex_bot 里建一支"漫剧制作组"，每个 bot 负责一段流程，由一个总导演统筹。所有 bot 共用一个规范化的项目目录。另外做一个画布网页，实时展示整体流程和进度。生图、生视频的模型可以替换和扩充。

**非目标（v1 不做）**：多用户 SaaS、计费系统、在画布上直接编辑内容、自动发布到视频平台。

---

## 2. 设计原则

1. **文件即状态**：项目目录里的 JSON 和文本文件是唯一事实来源。bot 之间的消息只做"通知 + 文件路径"，不在聊天里传正文。
2. **中心调度**：总导演一对多派活，专职 bot 之间不直接串联（受 nex_bot 委托深度限制，见 §10）。
3. **单写者**：每个文件或字段只有一个角色能写；共享清单统一通过状态工具修改。
4. **付费必审**：真实的生图、生视频提交都要先过预算闸门。闸门写在提交脚本里**强制检查**，不依赖 bot 的审批级别（nex_bot 会把总导演的审批级别带给它委派出去的工作，见 §9.3）。
5. **人在关键节点把关**：长篇 6 个审核点、短片 3 个审核点（§8、§8.6）。bot 不能自己把 `generated` 改成 `approved`。
6. **模型可替换**：bot 只描述"要生成什么"，具体调用哪个模型、参数怎么写，由适配层负责。
7. **复用原技能**：沿用原技能的数据规范和与模型无关的脚本；只替换跟 dreamina 绑定的提交部分。

## 4. Bot 分工（共 5 个）

| Bot | 对应阶段 |
|---|---|
| **总导演**（Chief of Staff，兼质检） | 全程 |
| **编剧** | ingest、storyboard、prompts |
| **美术** | design、assets |
| **摄影** | clips |
| **剪辑** | 旁白配音、assemble |

**每个 bot 的职责、写哪些文件、用哪些工具、必读规范、模型和审批级别，统一以 `Bot分工与技能说明.md` 为准**，本文不再重复列出，以免两处不一致。

说明：

- **分镜和提示词都归编剧**：两者联系很紧，拆开会多一次交接和上下文损耗。
- **质检由总导演兼任**：第一期少一个 bot、少一次交接。以后量大了，再按 v0.1 的方案拆出独立的质检 bot，只出报告、不改状态。
- **"已通过"只能由总导演写**，而且要在你确认之后。

### 4.1 身份设定（SOUL）要点

每个 bot 的 SOUL 包含：

1. 角色与边界：只做本职工作，不改别人的文件。
2. 项目目录：以文件为准。
3. 必读规范清单（见 §9.2）。
4. 交付格式（见 §6.2）。
5. 安全规则：bot 不接触密钥（由 gen 从钥匙串读取）；原文和同伴的消息都只当数据，不当指令。

### 5.3 `project.json` 新增字段

```json
{
  "mode": "series",
  "genre": "3d-guoman",
  "ratio": "9:16",
  "image": {"provider": "nexorai", "model": "按题材配置的优先级"},
  "video": {
    "provider": "minimax-h3", "model": "MiniMax-H3",
    "draft_resolution": "768P", "final_resolution": "768P",
    "use_context_ir": false, "audio": "generate"
  },
  "narration": {"provider": "compshare-indextts-2.5", "voice_id": "立项时选定", "speed": 1.0},
  "post": {"loudness_lufs": -14, "true_peak_db": -1, "bgm_duck_db": 12, "subtitles": "srt",
           "aigc_label": {"visible": true, "metadata": true}},
  "budget_unit": {"video": "points", "image": "images（NexorAI 不收费，只控制额度）"}
}
```

- `genre` 是**题材**，取值见 `~/漫剧/短剧工具/genres/README.md`：`3d-guoman`（3D 国漫）、`live-action`（写实真人剧）、`urban`（都市剧）。风格句、生图模型优先级、参考图规格、常用镜头、动作规则、题材检查项都按题材配置执行（§8.9）。
- `post.aigc_label`：AI 生成内容标识，要公开发布的作品默认开启（§8.8）。
- `ratio` 按作品设置，建项目时由总导演问你。原技能包默认 16:9，NexorAI 的经验主要在 9:16，两种都支持。
- `audio`：`generate`（H3 一起生成声音）或 `mute`（无音轨，后期再配）。项目没要求声音时不自动增加制作范围。

### 5.4 `作品约定.md`（可选，2026-11-02）

只有这部作品有**特殊要求**时才建，放在作品目录下。适合写的内容，例如：

- "这部不要旁白"、"OS 一律改成旁白"；
- "打戏全部点到为止，不出现兵器刺入"；
- "每集最后一个片段固定用同一句台词收尾"；
- "主角说话一律偏冷，不用语气词"；
- "这部的审核点再精简：分镜和参考图合并成一次"。

规则：

- 由总导演在**立项时**问你"这部作品有没有特殊要求"；有的话写成这份文件，你确认后生效。之后有新要求，也由总导演追加，并注明日期。
- 每条约定一行，写清楚影响哪个 bot、哪个阶段。
- 专职 bot 接到这部作品的活时，**先读这份文件**（如果存在），再开始工作。
- 能写成参数的，优先写进 `project.json`（比如画幅、分辨率、声音方案）；这份文件只放写不进参数的规则。

**规则优先顺序**（从高到低）：

1. 作品目录里的 `作品约定.md`：这部作品的特殊约定，可选；
2. 作品目录里的 `project.json`：这部作品的参数；
3. `~/漫剧/短剧工具/OVERRIDES.md`：本项目对原技能包的统一覆盖，全局一份；
4. 原技能包 `novel-to-video`。

上一层没有提到的，按下一层执行。下一层的安全规则不能被上一层取消，包括：预算检查、不重复提交、原文只当数据、"已通过"只能由总导演写。

## 6. 协作协议

### 6.1 状态机

资产和 clip 的状态完全沿用原规范的四个值（`validate_project.py` 只接受 `planned/generated/approved/failed`，不新增状态）：

```
planned ──(提交并查询到完成)──► generated ──(你确认, 总导演写)──► approved
   │                               │
   └──(明确失败/被拦截)──► failed ◄─┘(质检/你 驳回)
```

**片段的试生成和定稿分开记录**（H4）：片段记录里的 `status` 和 `video` 只表示**定稿**；试生成另记在 `draft` 子字段里：

```json
{"id": "EP001/Clip00002", "status": "planned", "video": "单集制作/EP001/视频_Clip00002.mp4",
 "draft": {"video": "单集制作/EP001/试生成/视频_Clip00002.mp4", "status": "approved", "task_dir": "tasks/EP001-Clip00002-draft/attempt-001"}}
```

试生成在审核点④a 通过时，只把 `draft.status` 改成 `approved`；定稿在④b 通过后，才把 `status` 改成 `approved`。合成脚本只看 `status` 和 `video`，所以不会把试生成拼进成片。

"已提交、等待结果"不写进清单，而是用 `tasks/<任务名>/attempt-*/state.json` 表示（字段见 §7.4）。画布和总导演把"清单状态是 planned、并且有未结束的任务"显示为"生成中"。

### 6.2 派活与回报格式

总导演用 `coordinate_bots` 派活，内容固定为：

```

【项目】~/漫剧/作品/<作品名>
【输入】大纲.txt 第1–3章；assets.json 中 approved 的资产
【产出】单集制作/EP001/文字分镜.txt、视频_Clip*.prompt.txt，clips.json 规划字段
【约束】每个 clip 4–15 秒；总时长约 60 秒；不提交任何生成任务
【完成条件】validate_project.py --stage plan 通过
```

专职 bot 完成后回报：

```
【结果】完成 / 部分完成 / 受阻
【产出】文件列表（相对路径）
【校验】运行了什么、结果如何
【花费】本次消耗的积分/张数（没有花费写 0）
【未完成/风险】……
【需要决定】……（没有就写"无"）
```

同时在 `logs/<bot名>.jsonl` 追加一行事件：`{"time","bot","stage","target","event","files","note"}`，供画布显示时间线。

### 6.3 共享清单的写入：`pipeline_state.py`


- 按 `--role` 限制能改的字段和能做的状态转换（例如只有总导演能写 `approved`）；

- `approvals/budget.json`：额度（`limit`）由总导演写；已用额度（`used`）**只由提交脚本写**。

## 7. 生成适配层（`tools/gen/`）

### 7.1 为什么需要

用户已经确认要用 NexorAI 和 MiniMax H3，而且以后可能接入别的模型。各家接口差别很大：参考图怎么传、提示词里怎么指代图片、时长范围、能不能混用首帧和参考图、任务状态的取值都不一样。如果把这些差别写进 bot 的技能里，每换一次模型就要改所有 bot。

所以把差别都收进适配层：**bot 只写与模型无关的"生成请求"，适配层负责翻译、提交、查询、下载、记账。**

### 7.2 统一的生成请求

**和 `h3_task.py` 的关系**（H2）：`gen` 只是统一入口，内部的 H3 部分直接调用 `skills/minimax-h3-video/scripts/h3_task.py`。**在 `gen` 写好之前，摄影一律直接用 `h3_task.py`**（它已经包含预算检查、防重复提交、承接句修改），不会出现两条提交路径同时存在的情况。

bot 写一份请求文件，交给 `gen` 执行：

```json
{
  "kind": "video",
  "purpose": "EP001/Clip00002",
  "pass": "draft",
  "prompt_file": "单集制作/EP001/视频_Clip00002.prompt.txt",
  "references": [
    {"label": "Clip00001-尾帧", "path": "单集制作/EP001/尾帧/Clip00001.png", "role": "reference"},
    {"label": "C00001-A", "path": "角色/C00001-A-林舟.png", "role": "reference"}
  ],
  "duration": 8,
  "ratio": "9:16",
  "audio": "generate",
  "output": "单集制作/EP001/试生成/视频_Clip00002.mp4"
}
```

- 提示词里用原技能的可读标记，例如 `[C00001-A]`、`[Clip00001-尾帧]`。适配层按各家规则替换：MiniMax 换成 `<Picture N>`，NexorAI/Grok 换成"图N"。替换前后的对照记录在 `request.json` 里。
- `role` 的通用取值：`reference`（参考图）、`first_frame`（首帧）、`last_frame`（尾帧）、`reference_audio`（音色模板）、`reference_video`（参考视频）。
- 分辨率、模型名都不由 bot 填写，而是从 `project.json` 和 `pass` 推出来。

### 7.3 统一命令

```bash
gen estimate <请求文件>                 # 只校验和估价，不花钱
gen submit   <请求文件> --task-dir <目录> # 过预算闸门后提交，记录任务 ID
gen query    --task-dir <目录>          # 查询一次；完成就下载到 output
gen pending  --project <作品目录>        # 列出所有未结束的任务（给例行任务用）
```

`submit` 的行为：

1. 按目标模型的能力描述校验参数（时长范围、参考图数量、模式能否混用等）。不合规就直接拒绝，不偷偷改参数。
2. 估算费用，向 `approvals/budget.json` 里对应的批次预占额度；额度不够就拒绝，并提示让总导演找你批准。**不带批次就不能提交**（`h3_task.py` 已经实现：`--budget`、`--batch` 必填；被拒绝、失败、拦截、取消的任务自动退回额度；结果不明的任务保持占用）。
3. 先写 `request.json`（不含密钥），再提交。
4. 记录任务 ID。如果提交超时、结果不明，状态记为 `unknown`。下一次先查任务列表找回任务，**不会自动重新提交**（沿用原技能的规则）。

### 7.4 任务状态（统一）

| 统一状态 | MiniMax H3 原始状态 | NexorAI 生图 |
|---|---|---|
| `submitting` | — | — |
| `pending` | scheduled / moderating / queued / running | —（同步接口，没有这个状态） |
| `succeeded` | succeeded | 返回了图片，并通过解码和尺寸核验 |
| `failed` | failed | HTTP 错误或返回里没有图片 |
| `blocked` | blocked（审核没通过） | 内容被拒 |
| `cancelled` | cancelled | — |
| `unknown` | 提交超时或无法解析任务 ID | 请求超时（结果不确定，不自动重试） |

注意：H3 在自动重试时会从 `running` 回到 `queued`，这不算失败。

### 7.5 能力描述（`profiles/*.json`）

每个模型一份，`gen` 用它来校验参数和估价；画布也读它，用来显示单价。

```json
{

  "kind": "video",
  "api": {"base": "https://cp.compshare.cn", "env_var": "MINIMAX_H3_API_KEY"},

  "ratios": ["adaptive", "21:9", "16:9", "4:3", "1:1", "3:4", "9:16"],
```

### 7.6 Provider：MiniMax H3（视频）

依据：<https://www.compshare.cn/docs/minimax-h3/api/minimax-h3-video-api>

- **鉴权**：使用 H3 专属密钥（前缀 `sk-ml-`），从 macOS 钥匙串读取（服务名 `MINIMAX_H3_API_KEY`），不写进任何文件或日志。
- **创建**：`POST /minimax/v2/video_generation`，带 `Idempotency-Key`，值为请求内容的哈希。同一份请求重复提交时，平台会返回原来的任务，这是平台这一侧的防重复保护。
- **参考图**：本机文件压成 JPG 后以 **Data URL** 内联上传，不需要公网图床。上传前检查单张不超过 30 MiB，整个请求不超过 72 MiB。
- **衔接方式**（H3 不允许首尾帧和参考图混用）：
  - 默认用"全能参考"：上一段的尾帧作为 `<Picture 1>`，加上角色、场景参考图，最多 9 张。这和原技能用多参考图做衔接的思路一致，只能保证接近，不能保证首帧逐像素相同。
  - 只有镜头不需要角色参考图，或者你明确要求严格接上首帧时，才改用 `first_frame` 模式，并在承接报告里写明代价（没有角色参考图，人物可能走样）。
- **时长**：本地制作限定 **4–15 秒的整数**。不使用适配器的更长时长扩展。`use_context_ir` 默认关闭；只有已有具体请求明确选择开启时才传 `--context-ir on`，不从历史样例继承。
- **声音**：默认音画一起生成；`audio=mute` 时传 `mute_audio=true`。中文对白在提示词里写成 `<d>[Chinese] …</d>`。
- **查询**：`GET /minimax/v2/query/video_generation/{task_id}`。成功后**立即下载** `content.url`，因为文档没说明下载链接的有效期。
- **回调**：需要公网地址，本机用不了，第一期不用回调，靠轮询（§8.3）。
- **余额**：`GET /minimax/v2/query/point_usage_summary`，总导演在申请批次额度前先查一下。

### 7.7 Provider：NexorAI（图片）

依据：`短剧工具/参考文档/使用NexorAI生成图片.md`（你写的规范），以及 2026-10-31 实测：[调研/NexorAI生图模型调研.md](调研/NexorAI生图模型调研.md)

- **计费性质**：不收费，但消耗账号额度。预算闸门照样按"张数"控制额度，金额记为 0。
- **实现**：`skills/nexorai-image/scripts/nexorai_image.py`（2026-11-03，先单独写，稳定后再接进 `gen`），规则和用法见 `skills/nexorai-image/SKILL.md`；模型优先级在 `profiles/nexorai.json`，测试核对它和 `genres/` 一致。
- **鉴权**：按顺序读环境变量 `NEXORAI_API_KEY`、Windows 凭据管理器（Mac 上原来是钥匙串）。
- **请求头**：必须带固定的 `User-Agent`，否则会被 Cloudflare 拦截（返回 `403 error code: 1010`）。
- **模型优先级**：**按题材不同**，以 `genres/<题材>.md` 为准。3D 国漫首选 `grok-imagine-image-quality`；写实真人和都市剧首选 `grok-imagine-image-2.0`。下表是 3D 国漫的排序，保留作参考（详见调研报告 §3）：

| 用途 | 首选 | 第二 | 第三 |
|---|---|---|---|
| 角色基础形态（文字生图） | `grok-imagine-image-quality` | `gpt-image-2.5-sunburst` | `grok-imagine-image-2.0` |
| 衍生形态 / 保持人物一致（改图） | `grok-imagine-image-quality` | `grok-imagine-image-2.0` | `gpt-image-2.5` |
| 场景图（16:9 或 9:16） | `grok-imagine-image-quality` | `grok-imagine-image-2.0` | `gpt-image-2.5-sunburst`（仅竖图） |
| 角色设定稿（多视图拼版，给人看，不当视频参考） | 按题材配置（`genres/` 第 2 节，2026-11-03 定：以题材配置为准）；题材配置没写时用 `gpt-image-1.5` | `gpt-image-2` | — |
| 写实风格作品 | `grok-imagine-image-2.0` | `gpt-image-2.5` | — |

  优先级写在 `profiles/nexorai.json` 的 `priority` 字段里，按用途分别列出。换成下一个模型要先经总导演同意（或者你同意），适配层不自动切换。`gemini-3.1-flash-image` 目前不可用（上游账号被停用），`gpt-image-2.5-flare` 和 2.5 几乎一样，这两个暂不列入。
- **纯文字生图**：`POST /v1/images/generations`。Grok **必须传 `aspect_ratio`**，`size` 参数无效。GPT 的 `size` 不可靠（请求 864×1536 实际返回 1024×1536，请求 1536×864 实际返回 1942×809），以实际尺寸为准。
- **带参考图**（衍生形态、保持人物一致）：`POST /v1/images/edits`，用 multipart 上传 `image[]`，参考图先压成 JPG；提示词里用"图1、图2"指代。
- **返回**：同时处理 `b64_json` 和 `url` 两种格式；终端和日志里不打印 base64。
- **尺寸核验**：按文档的"强制尺寸核验"执行，也就是解码后读出真实宽高、按严格比例判断、只裁切不拉伸，原图和交付图都保留，并在任务记录里写明做了什么处理。
- **超时**：单次请求最长 290 秒；超时算 `unknown`，不自动重试。
- **比例与角色两种图**：每个角色出两种图。视频参考图用项目画幅，单人、背景干净，存在 `image` 字段，传给 H3；三视图设定稿用横图（`character_sheet_ratio`），存在新增的 `sheet` 字段，只给人看。先用文生图出视频参考图，再以它为参考用改图接口出三视图。详见 `Bot分工与技能说明.md` §2.3。
- **三参考分工（2026-11-01，吸收自 open-pose-costume-skill）**：用改图接口时，人物、姿势、服饰三类参考各管一件事：
  - 人物图：管身份和画风；
  - 姿势图：管动作和视角，不带过来人偶线条和模特体型；
  - 服饰图：管穿搭，不带过来服装模特的脸和身材。

  提示词按职责分离来写；有几张图就编几个号，不引用不存在的图号。多张参考图用 `image[]` 依次上传。这套写法用于视频参考图、三视图和衍生形态（换装）。三张图一起融合时，Grok 能否按分工执行还没测，放进统一实验；如果不行，这类任务改用 `gpt-image-2`。评估见 `调研/open-pose-costume接入评估.md`。
- **姿势和服饰素材库（可选）**：用 `tools/pose_costume.py` 从 open-pose-costume 的公开目录里按编号或关键词查参考，只下载选中的原图到本机缓存 `~/漫剧/素材缓存/open-pose-costume/`。规则：
  - 自动排除自建素材（`source == "custom"`，这部分只限个人使用）；
  - 不放进作品目录，也不对外分享；
  - 只在现代题材，或者需要标准站姿、坐姿时使用。库里没有古风服装，也没有打斗姿势。
- **分辨率**：Grok 最大输出 720×1280，用作 H3 视频参考图足够（H3 会把短边超过 1080 的图缩小）。以后如果需要高清海报级素材，再接入付费的高分辨率模型。
- **以后接付费生图模型**：按 §7.8 加一个 provider，在能力描述里填上单价；预算闸门会自动按金额控制，不再只数张数。

### 7.8 以后接入新模型

1. 在 `providers/` 下新增一个文件，实现 `validate / estimate / submit / query / fetch` 五个函数；
2. 在 `profiles/` 下新增一份能力描述；
3. 在作品的 `project.json` 里把 `image.provider` 或 `video.provider` 改成新的名字。

bot 的技能、目录结构、状态机、画布都不需要改。

**接入第二个视频模型时还要做一件事**：目前的中文分镜规范（片段切分、逐秒指令、台词四种类型、承接、静默段）放在 H3 技能的 `storyboard.md` 里，但它大部分内容和模型无关。接第二个视频模型时，要把它移出来，做成**共用的分镜规范**；各个模型的技能只保留"中文分镜怎么翻译成这个模型的提示词"。只有 H3 一个视频模型时，先不移动。

**分层原则**（2026-11-02）：
- **模型专用层**（各模型技能）：提示词语法、模型特有的坑、提交脚本；
- **模型参数层**（`profiles/*.json`）：时长范围、参考数量、参考音频建议时长、单价；
- **共用层**（分镜规范、设计文档流程、语音识别质检、剪辑后期）：对所有模型生效。

例如"防止乱说话"：分镜里标出**静默段**属于共用层；静默段在提示词里写成 `silently` 或 `No one speaks` 属于 H3 专用层；语音识别检查多出来的人声属于共用层。同一部作品也可以中途换模型，因为每个任务记录里都有自己用的 provider 和模型，历史记录不会乱。

## 8. 端到端流程

```
你：「把《XX》第1–3章做成 3 集，每集约 1 分钟」
 │
 ▼ 总导演：建项目，问画幅/画风/声音，查积分余额，估算总花费 ──► ⏸ 审核点①：确认参数和第一批额度
 │
 ├─► 编剧：ingest（大纲 + 资产清单 + 资产详情）
 ├─► 美术：design（风格基准 + 资产提示词）              ← 可以和编剧写分镜并行
 ├─► 编剧：storyboard + prompts（逐集；提示词是草稿版，承接句用 {{承接定义/承接开场：…}} 标出）
 ├─► 总导演质检：分镜与提示词 ─────────────────────────► ⏸ 审核点②：确认分镜
 ├─► 剪辑：用语音合成配好全部旁白，只记录旁白实际时长（narration_duration）；超时的片段由编剧调整（§8.5.5）
 │
 ├─► 美术：assets（NexorAI 生图 + 尺寸核验）
 ├─► 总导演质检：逐张看图 ──────────────────────────────► ⏸ 审核点③：确认参考图
 ├─► 编剧：按通过的参考图回填提示词的 subject_definitions；按旁白实际时长调整超时的片段（H5、H6）
 │
 ├─► 摄影：按已批准请求默认 768P；首次说话结果可截音色模板，再按依赖顺序推进
 │        承接片段：摄影看过上一段的真实尾帧后，用 h3_task.py set-continuity 只改承接句，再提交
 ├─► 总导演质检：抽帧看片、台词识别比对 ─────────────────► ⏸ 审核点④a：确认动作、衔接和各角色音色
 ├─► 摄影：已合格结果直接采用；仅已批准返工再生成，尾帧从实际采用视频提取
 ├─► 总导演质检：抽帧看片、核对音轨和时长 ───────────────► ⏸ 审核点④b：确认定稿片段
 │
 ├─► 剪辑：assemble（拼接 + 旁白 + 配乐 + 响度 + 字幕 + 校验，§8.5.3）
 └─► 总导演：汇报产物路径、花费、质检结论和已知问题 ──────► ⏸ 审核点⑤：确认成片
```

### 8.1 试生成与定稿

默认均为原生 768P；480P 只用于用户明确要求的试片，不强制每段生成两遍。首次正式片段可以兼作定音素材，实际试听后截取干净模板。已经批准的同一音色不重复确认。

480P 重新生成 768P 是新的生成，画面可能改变；费用以实际请求和已有批次为准，不能把这里的历史价格当作当前报价。每次生成都核对原话、说话人物、音色、空间与动作完成。

连续片段从实际采用的上段提取尾帧并查看，不能以计划画面或旧试片替代。用户采用试片作为定稿时按已有决定同步状态，记录实测尺寸和已接受偏差，不自动放大或再生成。

### 8.2 分批派活

每次派活控制在大约 20 分钟内能完成的量（例如"一集的分镜"或"5 个资产图"），避免超过 nex_bot 的协作时限。

### 8.3 视频的提交和等待

摄影提交视频后，把任务 ID 记在 `tasks/` 下，然后**结束这一轮**，不在对话里等。

- **例行任务归摄影**（M3）：每 5 分钟唤醒摄影一次，对所有未结束的任务各运行一次 `h3_task.py query`（`gen` 完成后改为 `gen pending` 加 `gen query`）。
- **有结果时**：下载、校验，把对应状态改成 `generated`（试生成改 `draft.status`），再通知总导演（专职 bot 只能联系总导演，正好可行）。**没有变化时不通知**，以免刷屏。
- **结果是 `blocked`（审核没通过）**：把原因交给总导演，由你决定怎么改提示词；额度自动退回。
- **单个任务等满 60 分钟还没结束**（M2）：报告总导演，保留任务 ID 继续查，不算失败，也不重新提交。

### 8.4 返工

质检不通过时，总导演用 `coordinate_bots` 的 `rework=true` 让原来的 bot 修改；同一个问题最多改两轮（沿用原规范），还不过就停下来问你。

### 8.5 声音与后期（2026-11-01 确定）

总体分工：**台词、同步音效、环境声由 H3 和画面一起生成；配乐、音量统一、字幕在剪辑阶段统一处理。** 每部作品可以在 `project.json` 里设 `audio: mute`，改为全部后期制作（方案 B，暂不实现，只预留开关）。

#### 8.5.1 角色音色模板：以第一次开口为准

每个片段的声音都是单独生成的，为了让同一个角色的声音前后一致，做法如下：

1. **定音台词**：编剧写分镜时，为每个会说话的角色标出他第一次开口的那句，作为"定音台词"。这句台词最好满足三个条件：
   - 时长 3 秒以上，太短的话，同一片段里这个角色的几句可以合起来用；
   - 只有这个角色在说话，不和别人的台词重叠；
   - 说话时没有很响的音效盖住（比如爆炸、兵器撞击）。
   
   如果他第一次开口的台词不满足这些条件，就顺延到最早一句满足条件的台词。
2. **定音批次**：试生成时，先生成每个角色的"定音片段"（含定音台词的片段）。有承接关系的，连同它依赖的前序片段一起先做。
3. **截取模板**：摄影用语音识别找到定音台词在视频里的时间位置，截出来，作为这个角色的音色模板（`音色/C00001.wav`，单声道，前后各留 0.2 秒）。**时长按当前视频模型的能力描述来定**：H3 是 3–5 秒、建议约 4 秒（社区反馈参考音频太长会导致开头出乱语）；换成其他模型时，按那个模型的建议值来截。
4. **你确认音色**：在审核点④a 里，除了看画面，还要听每个角色的音色模板。模板登记在作品目录的 **`voices.json`**（H9），按角色编号记录：
   ```json
   [{"character": "C00001", "file": "音色/C00001.wav", "source_clip": "EP001/Clip00005", "start": 3.2, "end": 7.9,
     "text": "哼，你以为我会怕你？", "status": "approved", "forms": ["C00001-A", "C00001-B"]}]
   ```
   摄影截取后写入，状态为 `generated`；你确认后，由总导演改成 `approved`。
5. **之后统一引用**：这个角色在其他所有片段里出现并说话时，都把模板作为 `reference_audio` 上传（H3 技能里的写法：`[C00001音色参考] is the voice-timbre reference for <Subject N> (Sx).`）。定稿阶段，**包括定音片段自己在内**，所有片段都带上模板，这样定稿版本的音色是统一的。

补充规则：
- 模板跟着**角色编号**走（`C00001`），不跟着形态走（`C00001-A`、`C00001-B` 共用同一个模板，列在 `forms` 里）。只有年龄、物种这类会改变声音的形态变化，才另做一个新模板，在 `voices.json` 里另起一条，`character` 写成形态编号（例如 `C00001-C`）。
- 模板跨集复用：后面几集直接引用，不再重新定音。
- 一个片段最多只能上传 3 段参考音频（H3 的限制），正好对应"一个片段最多 3 个重要角色"的规则。
- 模板确认之前，角色的声音只靠角色卡里的音色描述句；模板确认之后，描述句仍然保留，和模板一起用。
- 你听了不满意时：换一句定音台词，或者重新生成定音片段（计入试生成额度）。
- 风险：官方说明参考音频"只引导，不保证保留原录音"；也有社区反馈加了参考音频后出现乱语（目前只见于本地部署版）。这些在 P0 完成后的验证里一起测。

#### 8.5.2 语音识别对齐（字幕、截取模板、台词质检共用）

一个工具 `tools/audio/align.py`，输入片段视频和分镜里的配音版台词，输出每句台词的起止时间、识别出的文字，以及和剧本的差异。三处共用：

| 用途 | 怎么用 |
|---|---|
| 截取音色模板 | 找到定音台词的起止时间 |
| 台词质检 | 识别文字和配音版台词对比，发现吞字、改词、漏句、多出来的乱语，写进质检报告 |
| **乱说话检查**（对所有视频模型生效） | 两项专门检查，任何一项不通过，这个片段就判为不通过并说明原因：① **开头 1 秒**内出现剧本里没有的人声；② 台词时间段**以外**出现人声（包括分镜里标的静默段、旁白段） |
| 字幕 | 字幕**文字用剧本里的配音版台词**（不用识别结果，避免识别错字），**时间轴用识别结果**；合成后按片段在成片里的位置换算成全片时间 |

识别引擎在 P0 里选定，候选是本地运行的 Whisper 系列（faster-whisper、whisper.cpp）和 FunASR（Paraformer，中文效果好、自带时间戳）。不把音频上传到外部服务。

#### 8.5.3 合成顺序（剪辑）

```
已通过的定稿片段
  → ① 统一尺寸、帧率、音频采样率（现有 assemble_clips.py）
  → ② 每段对白响度预先拉齐（防止片段之间忽大忽小）
  → ③ 拼接
  → ③b 混入旁白（旁白期间压低 H3 原声和配乐）
  → ④ 配乐：整集一条，在有对白的地方自动压低（sidechain ducking）
  → ④b 开头人声处理：只有经总导演确认"开头约 0.5 秒有乱语、这段本来没有台词"的片段才做，把这段的人声换成环境声，或者淡入
  → ⑤ 整体响度标准化
  → ⑥ 字幕：生成 成片.srt；需要的话再压一版带字幕的视频
  → ⑦ 校验：完整解码、时长、音轨、响度实测值、字幕时间不越界
```

音量默认值（写在 `project.json`，可按平台调整）：

| 项目 | 默认值 | 说明 |
|---|---|---|
| 成片整体响度 | -14 LUFS | 短视频平台常用的目标值（行业惯例，不是平台官方要求） |
| 峰值上限 | -1 dBTP | 防止平台转码后破音 |
| 配乐相对对白 | 有对白时压低约 12 dB，无对白时恢复 | 用 FFmpeg 的 sidechaincompress 实现 |

#### 8.5.4 台词的四种类型

分镜里每句台词都要标明类型，具体写法见 H3 技能 `audio.md` 的"台词的四种类型"：

| 类型 | 由谁生成 | 说明 |
|---|---|---|
| 对白 | H3 | 说话的人动嘴 |
| 画外对白 | H3 | 说话的人不在画面里，画面里所有人闭嘴 |
| OS（内心独白） | H3 | 角色自己的声音，嘴闭着，配表情和呼吸 |
| **旁白** | **后期语音合成**（§8.5.5） | 不写进 H3 提示词 |

#### 8.5.5 旁白：后期配音（2026-11-01 确定）

旁白和画面里的口型无关，所以不交给 H3，单独配音。好处是：音色整部剧完全一致；语气和停顿可以精确控制；改旁白不用重新生成视频。

1. **立项时定旁白音色**：总导演请你从语音合成服务的音色里选一个旁白音色（审核点①），记进 `project.json` 的 `narration` 字段，内容包括服务商、音色 ID、语速。第一人称小说如果"旁白就是主角本人"，也可以用主角的音色模板克隆出一个音色（看服务商是否支持）。
2. **先配旁白，再核对片段时长**（H6）：
   - 编剧写分镜时，按旁白语速**约每秒 4 字**给旁白预留时间，并写清旁白从片段的第几秒开始；
   - 分镜通过（审核点②）后，剪辑马上用语音合成配好所有旁白，存到 `单集制作/EP001/旁白/Clip00003-1.wav`，**只把实际时长写进 `narration_duration` 字段**，不改片段时长；
   - 实际时长超出预留的，由编剧调整这个片段的分镜和提示词，可以加长片段或者改短旁白。超出 1 秒以上的，总导演要告诉你；
   - 旁白音频在审核点③给你试听。
3. **生成视频时给旁白留出空间**：旁白时间段里，H3 不安排任何对白和 OS，并写上 `No one speaks during this shot; all characters keep their lips closed.`，环境声照常生成。
4. **合成时混进去**：剪辑把旁白按"片段在成片里的位置 + 分镜写的起始秒"放进成片。旁白期间，H3 原声（环境声）压低约 6 dB，配乐压低约 12 dB；之后再做整体响度标准化。
5. **字幕**：旁白的文字和时间直接来自旁白音频本身，不需要语音识别；字幕样式和对白区分开。
6. **台词写法**：旁白也写"配音版"，用 IndexTTS 2.5 自带的语速、情绪和读音控制来调整语气（具体参数在 P0 接入时核对）；语气主要还是靠台词字面（语气词加标点）。这些控制只用于旁白，不能写进 H3 提示词。

**已定：旁白配音用优云智算的 IndexTTS 2.5**（2026-11-02，你决定不用 oh-my-voice）。
- 和 H3 在同一个平台，**共用同一把 `sk-ml-` 密钥**（钥匙串 `MINIMAX_H3_API_KEY`），积分也共用。
- 接口（`https://cp.compshare.cn`）：创建任务 `POST /audio/v1/speech/jobs`（必须带 `Idempotency-Key`）；查询 `GET /audio/v1/speech/jobs/{task_id}`，成功后从 `output_url` 下载 WAV；音色列表 `GET /audio/v1/voices`；计价和余额 `GET /audio/v1/pricing`。另有参考音频上传和自定义音色（克隆）接口。
- **计费**（2026-11-02 实测 `pricing`）：**每 100 个字 1 积分**，一集 1 分钟的旁白大约 2–3 积分，成本可以忽略。
- **音色**（2026-11-02 实测 `voices`）：目前有 6 个中文预设音色：承泽（中低音、有力量）、晚晴（通透、自信）、知夏（轻快亲切）、明川（有活力、自然）、小新、猴哥；也可以上传参考音频做自定义音色。
- 支持中文、英文、日文、西班牙语、阿拉伯语；可以调语速和情绪，可以指定个别字词的读音（适合处理多音字）。
- 请求体字段已核对（2026-11-05，官方文档）：`text`（≤2000 字符，只按字母/汉字/数字计费）、`language`（ZH/EN/JA/ES/AR）、`voice.source=preset` + `voice.voice_id`、`speed`（0.5–2.0）、`auto_emotion`（默认 true）、`emotion_vector`（8 维情绪，须 auto_emotion=false）、`pronunciations`（读音规则）。任务状态 `queued/generating/succeeded/failed/cancelled`，成功从 `task.output_url` 下载，计费字段 `point_cost`/`point_status`（reserved→consumed/released）。文档：<https://www.compshare.cn/docs/minimax-h3/api/text-to-speech-api>。
- 接入方式：作为生成适配层的 `kind: speech`，和 `h3_task.py` 一样带预算检查、幂等键、结果不明不重复提交。
- 旁白音色：立项时总导演把预设音色的试听链接给你选；需要专属旁白时，用参考音频做一个自定义音色，整部剧复用。

#### 8.5.6 配乐：来自你提供的曲库（2026-11-01 确定）

- **位置**：`~/漫剧/曲库/`，所有作品共用，bot 只读。
- **曲目登记**：曲库里放一份 `曲库.json`，每首歌一条记录：
  ```json
  {"file": "古风/山河远.mp3", "title": "山河远", "mood": ["悲壮", "辽阔"], "tempo": "慢",
   "duration": 182, "loopable": true, "license": "已购，可商用", "note": "1:05 处有高潮"}
  ```
  `mood`、`tempo`、`license` 由你填写；`duration` 由工具自动读取。bot 听不出音乐的好坏，所以选曲**主要依据你的标注**。
- **选曲**：剪辑按每集的情绪走向，从曲库里挑 2–3 首候选，说明为什么选，交给你选定。可以整集用一首，也可以按段落分几首，分段时在段落之间做交叉淡入淡出。
- **长度对齐**：曲子比成片长就淡出；比成片短，标了 `loopable` 的就循环，没标的就换一首或者分段使用。
- **版权**：`license` 为空的曲目不会用在要公开发布的成片里，只能用于内部预览。
- P0 先把"给定一首配乐就能完成混音"的流程做好，选曲流程在 P3 里跑通。

### 8.6 短片模式（2026-11-01 确定）

用来做 **1–2 分钟的独立故事**。在 `project.json` 里设 `"mode": "short"`，默认是 `"series"`（长篇连载，即上面 §8 的流程）。两种模式共用同一套 bot、技能和工具，只有流程开关和几条检查规则不同。

#### 8.6.1 和长篇模式的区别

| 方面 | 长篇模式 `series` | 短片模式 `short` |
|---|---|---|
| 输入 | 长篇小说，指定章节 | 短篇故事、一段剧本，或者一句话创意 |
| 故事 | 按章节读原文、写大纲 | 原文较短时直接整理；**只有创意时，编剧先扩写成一页故事梗概** |
| 结构 | 每集：开头钩子 → … → 结尾留悬念 | 整片：**开头 3 秒钩子 → 冲突升级 → 反转或揭晓 → 收尾落点**；结尾必须收住，不留悬念 |
| 规模（约） | 按集数定 | 60–120 秒；8–15 个片段；2–4 个角色；2–3 个场景 |
| 审核点 | 沿用本片既有节点 | 最终视频词与结果在原节点确认；内部材料不重复送审 |
| 试生成 | 默认 768P，非必经阶段 | 同左；480P 仅在用户明确指定时使用 |
| 音色模板 | 从已批准的首次说话结果提取 | 同左；无额外定音试片的默认要求 |
| 配乐 | 每集选曲 | 整片一首 |
| 字幕 | 默认生成 `成片.srt`，需要时再压进画面 | **默认压进画面**（短视频平台一般都要求带字幕），同时保留 `成片.srt` |
| 旁白 | 后期配音 | 同样后期配音；解说式的短片可以大量使用旁白 |
| 跨集复用 | 资产编号、音色模板跨集复用 | 不涉及 |

#### 8.6.2 短片模式流程

```
你：「做一个 90 秒的短片：<故事 / 剧本 / 一句话创意>」
 │
 ▼ 总导演：立项（mode=short），问画幅、画风、旁白音色，估算花费
 ├─► 编剧：故事梗概（只有创意时扩写）→ 资产清单 → 分镜 + H3 提示词（标出"需试生成"的片段和定音台词）
 ├─► 美术：风格基准 + 资产提示词（与编剧并行）
 ├─► 总导演质检 ───────────────────────────► ⏸ 审核点①：故事梗概 + 制作参数 + 分镜 + 额度（一次确认）
 │
 ├─► 剪辑：配好旁白，只记录旁白实际时长；超时的片段由编剧调整
 ├─► 美术：参考图（视频参考图 + 三视图）
 ├─► 总导演 ──────────────────────────────► ▸ 快速确认：参考图（只看图，回复"可以"或指出要改的角色）（H10）
 ├─► 摄影：首次正式说话片段默认 768P → 实际试听后截音色模板
 ├─► 总导演质检 ───────────────────────────► ⏸ 审核点②：角色音色 + 旁白试听
 │
 ├─► 摄影：按已批准片段请求生成，默认 768P，绑定实际说话人的音色
 │      总导演按质检规则把关，只有超出两轮返工、花费超额或需要创作决定时才找你
 ├─► 剪辑：拼接 + 旁白 + 配乐 + 响度 + 压字幕 + 校验
 └─► 总导演：汇报 ─────────────────────────► ⏸ 审核点③：确认成片
```

#### 8.6.3 花费参考（90 秒，H3）

| 做法 | 积分 |
|---|---|
| 全部先试生成再定稿 | 约 90 × 15 = 1350 |
| 约三分之一的片段做试生成（短片模式默认） | 约 1050 |
| 全部直接出 768P | 约 900（出问题重做时按全价计） |

生图走 NexorAI，不花钱，只消耗额度。

#### 8.6.4 检查规则的调整

- 分镜自查：短片模式检查**结尾有没有收住**（反转、揭晓或情绪落点），而不是"有没有留悬念"。最后一个片段的类型可以是"钩子"之外的任意类型。
- 编剧在每个片段上标 `需试生成：是/否`；质检不通过先诊断实际请求和媒体；只有已批准的具体返工才再生成，不自动补做 480P。
- 总导演在短片模式下，对中间的片段**自行把关**。以下三种情况才找你：同一问题返工两轮仍不通过；花费超出批准的额度；需要做创作上的决定（例如改剧情）。

### 8.7 多部作品同时制作（2026-11-02 确定）

一套 5 个 bot 可以同时推进**约 3 部**作品。作品之间的数据本来就按作品目录隔离；下面这几条，是为了让它们在**线程、额度、并发、查询、调度**这几方面也不互相干扰。

#### 8.7.1 每部作品一个线程

- nex_bot 的每个 bot 可以同时运行多个线程（默认 3 个，在设置 → 常规 → 并行线程里可调成 1–10，已在源码中确认）。
- **现行作品隔离**：所有操作绑定作品绝对目录与具体版本；按当前工具和已有授权决定是否委派。历史 start_thread 方案不作为自动创建线程的要求，机械步骤在本任务批量处理。
- 总导演自己也是每部作品一个线程；你和总导演聊某部作品时，在对应的线程里聊。
- 每个 bot 的并行线程数建议设为 3。超出的消息会自动排队。
- `start_thread` 按作品分线程派活的实际效果，在 P1 里验证。

#### 8.7.2 作品清单

`~/漫剧/作品清单.json` 由总导演维护，记录每部作品一行：

```json
[{"name": "养儿方知父母恩", "dir": "~/漫剧/作品/养儿方知父母恩", "mode": "series", "status": "进行中",
  "stage": "EP002 试生成", "waiting_on": "你：审核点④a", "priority": 1, "threads": {"总导演": "<线程 id>"}}]
```

- `status` 的取值：`排队`、`进行中`、`等你审核`、`暂停`、`已完成`。
- **调度规则**：总导演按 `priority`（数字越小越优先）推进；"进行中"的作品不超过 3 部，多出来的排队等待。
- 画布首页读这份清单（§11）。

#### 8.7.3 全局账本与并发上限

所有作品共用同一个 H3 积分账户和同一个 NexorAI 额度。**花钱只按每部作品控制**（2026-11-03 你决定）：每部作品的上限就是它 `approvals/budget.json` 里你批准的批次额度；**不设全局积分上限**，全局的上限就是账户余额本身。全局这一层只管并发和记账。全局设置放在 `~/漫剧/全局设置.json`：

```json
{"h3": {"max_running_tasks": 3},
 "nexorai": {"images_cap_per_day": 50, "images_per_batch": 12, "max_running": 2},
 "active_projects_max": 3}
```

- 提交脚本（`h3_task.py` 和 NexorAI 生图脚本）在检查作品批次之后，再检查两件事：
  - **账户余额**：查 H3 余额，扣掉这次的预估后不能小于 0（余额不够平台本来也会拒，这里只是提前给出清楚的提示）；
  - **全局并发**：扫描所有作品里还没结束的任务，不能超过 `max_running_tasks`。
- 超出时：
  - **并发**超出：不报错、不重试，返回"排队中"，由总导演稍后再提交；
  - **作品批次额度**或**余额**不够：**直接拒绝**，提示找你追加额度或充值。不能返回"排队中"，否则会一直排下去、反复重试。
- 全局账本只追加记录，每笔都写明作品名、批次、任务目录、积分，以及是预占、退回还是**实际扣费**。任务结束后按平台返回的实际用量（`usage`）记一笔对账，和预占的估算值的差额也记下来。作品自己的 `budget.json` 照常维护，和全局账本互相可以对账。
- `全局设置.json` 只由你改（总导演和其他 bot 都不能改）；提交脚本只读它。

#### 8.7.4 一个全局查询任务

不再给每部作品各开一个查询任务，改成**一个全局例行任务**，归摄影：

- 每 5 分钟唤醒摄影一次（在摄影专门用于查询的线程 `【查询】` 里），扫描作品清单里所有"进行中"作品的未结束任务，各查一次；
- 有结果时，下载、校验、更新状态，然后**通知对应作品的总导演线程**；没有变化时不通知；
- 需要一个汇总命令 `h3_task.py pending --all`（P0 实现），一次列出所有作品的未结束任务。

#### 8.7.5 审核攒批

- 同一类审核（例如几部作品的分镜，或者几部作品的参考图）尽量攒在一起，一次交给你；
- 审核包 `reports/审核点N.md` 的开头写明作品名、集数、本次需要你决定的事项；
- 同一部作品里，紧急的审核（比如额度用完、内容被拦截）随时报告，不需要攒批。

#### 8.7.6 规模再大时

- **同时 5 部以上**：复制出第二套制作组（nex_bot 里新建一个团队，有自己的总导演），按题材或作品分配。工具、技能、作品清单、全局账本和全局设置仍然共用一套。
- **硬限制**：bot 运行命令依靠这台 Mac 上的 NexBot 客户端在线，出片期间这台 Mac 不能关机或休眠。规模更大时，再考虑把执行环境搬到服务器（P4）。

### 8.8 AI 生成内容标识（2026-11-02 确定）

依据《人工智能生成合成内容标识办法》（2025 年 9 月起施行），公开发布的 AI 生成视频要加**显式标识**（观众看得见）和**隐式标识**（写在文件元数据里）。写实真人题材风险最高，但所有题材都要加。

- **做法：后期统一加**（不使用 H3 的 `aigc_watermark`，以便统一控制标识的样式和位置）。
  - **显式**：成片开头 3 秒内显示一行提示，例如"本片含 AI 生成内容"；同时在角落持续显示小号角标（位置和文字写进 `project.json`，默认右上角"AI 生成"）。由剪辑在合成的最后一步加。
  - **隐式**：在成片的元数据里写入 AI 生成说明（FFmpeg 的 `-metadata comment=...`），校验时检查是否写入。
- `project.json` 的 `post.aigc_label` 控制开关；只做内部预览的版本可以关闭，**要公开发布的成片必须开启**。总导演在审核点⑤汇报时要写明标识是否已加。
- 标识的具体文字和平台要求可能会更新，正式发布前由你按平台的最新规则确认一次。
- 另外要求：角色不能像真实存在的人，不用真人照片作参考，不在提示词里写真人姓名（题材配置里有具体检查项）。

### 8.9 题材配置（2026-11-02 确定）

- 作品的题材写在 `project.json` 的 `genre`，配置文件在 `~/漫剧/短剧工具/genres/`。第一批支持三种：`3d-guoman`、`live-action`、`urban`（都市剧以真人剧为基础）。
- 题材配置属于**共用层**：写这个题材要什么效果，和具体的视频模型无关。各题材的英文风格句示例、在 H3 上的写法，见 H3 技能 `visual-and-camera.md`。
- 每份配置包括：风格句、生图模型优先级、参考图规格、常用镜头、动作与表演、声音偏好、题材检查项、素材库能不能用、合规要求。
- 总导演立项时问你题材；编剧、美术、摄影接到这部作品的活时，先读对应的题材配置。
- 镜头的选择统一使用共用层的 `镜头语言手册.md`，它按剧情功能给出了分题材的镜头方案。
- **近景问题**：社区实测，全参考模式下开场拍不出稳定的近景。先在统一验证里实测；如果确实不行，再给近景多的题材（真人剧、都市剧）加一个**可选首帧**开关，只在需要的片段启用，不改默认流程。

### 8.10 复盘与经验沉淀（2026-11-02 确定）

每做完一集（长篇）、一章（读原文、写大纲阶段）或一个短片，总导演都要**自动复盘**：整理这一轮遇到的坑和问题，交给你看；**你确认之后**，才把规避方法写进对应的技能或配置文件。

#### 8.10.1 什么时候复盘

| 时机 | 复盘范围 |
|---|---|
| 一集成片通过审核点⑤（长篇） | 这一集从分镜到合成的全过程 |
| 一章读完、大纲和资产清单通过（长篇） | 读原文、写大纲、抽资产的问题 |
| 一个短片成片通过（短片） | 全过程 |
| 一集或一个短片**中途放弃** | 到放弃为止的过程，重点写放弃原因 |

没有值得记录的问题时，也要给出一份简短的复盘（"本集无新问题"，并列出花费和返工次数），不要跳过。

#### 8.10.2 复盘的依据（不能凭印象写）

总导演从文件里收集证据：

- `reports/` 里的质检报告和审核记录（包括你在审核点提出的修改意见）；
- `tasks/` 里的任务记录：失败、被拦截、结果不明、重做了几次；
- `logs/` 里各 bot 的事件和返工记录；
- 语音识别比对结果：乱说话、吞字、改词；
- 预算：计划花费和实际花费的差距；
- 承接句的修改日志（`*.continuity.jsonl`）。

#### 8.10.3 复盘报告：`reports/复盘-EP001.md`（短片是 `reports/复盘.md`）

开头是一张汇总表：本轮的片段数、试生成和定稿的次数、返工次数、被拦截次数、计划花费和实际花费、用时。然后**每个问题一条**：

```text
### 问题 3：竖屏横移时复制出第二个林晚
- 现象：EP001/Clip00007、Clip00011 两段，横移镜头里出现两个相同的人
- 证据：tasks/EP001-Clip00007-final/attempt-002、质检报告 reports/质检-EP001.md 第 4 条
- 影响：重做 3 次，多花 75 积分
- 原因判断：推测（已有规则 H3 坑 26 说过竖屏横移容易复制人物）；本作品出现 2 次
- 是否已有规则：有（H3 坑 26，状态"待验证"），但编剧没有写"画面中只有这一位人物"
- 建议规避：
  1. 编剧：竖屏横移的单人镜头必须写 "Only <Subject 1> appears in the frame throughout."（写入 H3 技能 storyboard.md 自查清单）
  2. H3 坑 26 的状态从"待验证"改为"已证实（本作品 2 次）"
- 写入位置：skills/minimax-h3-video/references/storyboard.md、pitfalls.md
- 适用范围：所有作品 / 所有使用 H3 的作品
- 可信度：已证实（2 次，有文件为证）
```

最后附上"**有效做法**"：这一轮里证明有用、值得推广的写法，也按同样的格式写。

#### 8.10.4 写入哪里（按分层原则）

| 问题属于 | 写入 |
|---|---|
| 只和这部作品有关（某个角色、某种特殊设定） | 作品目录的 `作品约定.md` |
| 和题材有关（真人剧的手指、都市剧的画面文字） | `genres/<题材>.md` 的"实战经验"一节 |
| 和视频模型有关（H3 的写法、坑） | 模型技能，例如 `skills/minimax-h3-video/references/pitfalls.md` 或对应的规范文件 |
| 和生图模型有关 | 美术的 NexorAI 技能（P0 编写） |
| 和镜头选择有关（与模型无关） | `镜头语言手册.md` 的"实战经验"一节 |
| 和某个 bot 的工作方式有关（漏了步骤、回报不清） | `bots/<bot>/SKILL.md` 的"实战经验"一节 |
| 和流程、协作有关 | 设计文档或 `OVERRIDES.md`（按已有整体优化授权维护，不另加逐条确认） |

#### 8.10.5 确认与写入规则

1. **沿用已有维护授权**：用户已要求整体优化、补经验或统一规范时直接落实，不再逐条重复确认。实际超出已授权范围的实质改变才具体说明；不能把整体原话伪装为逐项另行批准。
2. **观察与规则分开**：记录实际次数、证据与适用范围。问题重复出现不证明某个修法或原因正确；规则升级需要可靠依据或重复正向验证，不机械以两次出现升级。
3. **表格与正文分别维护**：经验表通过 lessons.py 事务修改；对应技能正文在已有优化授权范围内同步，消除冲突旧指令并保留变更依据，不为可逆维护再开确认。
4. **先查重和冲突**：已有经验更新原条，按当前用户要求及规则优先级统一旧文本；只有上下文无法决定的实质取舍才提问。
5. **有记录、可撤销**：
   - 每次写入，都在 `~/漫剧/经验库.md` 登记一行：编号、日期、来源作品和集数、写到了哪个文件、一句话内容、你确认的原话；
   - 工具目录与漫剧数据目录是独立本机 Git 仓库。经验写入默认不提交、不推送；`commit <操作编号>` 只预览，另行获得用户批准后才能 `--execute --confirm`。预先暂存内容、参与文件夹带其他修改、HEAD 改变或配置要求人工钩子/签名时拒绝工具提交，不清理用户状态。
   - 每次变更在 `经验操作/Lxxx.json` 保存具体前后行及最小变更片段。撤销根据操作记录核对当前行、恢复旧值并追加撤销登记；旧记录缺少证据时不猜测，不能用一次 git revert 代替两个仓库和经验登记的完整撤销。
6. **用工具写，不手改**：`tools/lessons.py` 当前支持题材、镜头手册、NexorAI、H3 坑表、作品约定及 postproduction 后期规范六类目标。仅写精确的实战经验节或已知坑表，不改正文。岗位正文与对应规范在用户已有整体维护授权内同步，工具仍只精确修改允许的经验表；不为每条经验重复确认。
   - 命令：add（新增）、update（更新经验方法/等级/次数/证据）、pitfall（坑表新增/改状态）、list/status（只读）、retract（按操作记录撤销）、recover（恢复已确认的文件事务）、commit（独立 Git 预览/执行）。修改与恢复需要确认原话；只读命令不要求 --confirm，不创建登记或锁文件。
   - 经验编号 Lxxx 是全局操作编号：新增、更新、撤销各自登记一条；更新保留目标表原经验编号，输出的新编号用于追溯和撤销本次更新。Git 回执独立保存于 `经验操作/提交回执/`，不回写已提交的登记形成自引用。
   - 同一根使用经验操作锁。中断后核对参与文件前后指纹，再恢复原操作；检测到用户插入的修改就停止，不强行回滚。多文件写入可恢复，不宣称具有文件系统级整体原子性。
7. **保持精简**："实战经验"一节超过 20 条时，总导演在复盘里提议合并或删除过时的条目，由你确认。

#### 8.10.6 和 nex_bot 技能的关系

导入 nex_bot 的岗位 `SKILL.md` 只放**稳定的工作流程和"去读哪些文件"**，具体的规则和经验都放在工具目录的文件里，bot 每次工作时按需读取。这样经验写入后**马上对所有 bot 生效**，不需要在 nex_bot 里重新导入技能，也不会和 nex_bot 自带的技能修改流程（需要在应用里逐条确认）冲突。

## 9. nex_bot 配置

### 9.1 团队设置

1. 新建分区（团队）"漫剧制作组"，放入 5 个 bot。
2. 把"总导演"设为该分区的 **Chief of Staff**。
3. 每个专职 bot 允许联系的对象（peers）**只填总导演**。
4. 所有 bot 的工作目录设为 `~/漫剧/作品`。
5. 模型**按岗位分配**：

| Bot | 模型要求 | 建议的对话模型（NexorAI） |
|---|---|---|
| 总导演（兼质检） | 要能看图、推理能力强（质检要看参考图和抽帧） | `claude-opus-5-5` |
| 编剧 | 长上下文、强模型 | `claude-opus-5-5` |
| 美术 | 要能看图（核对生成的参考图） | `claude-sonnet-5-5` |
| 摄影 | 要能看图（核对尾帧和抽帧） | `claude-sonnet-5-5` |
| 剪辑 | 便宜模型即可 | `claude-haiku-5-5` |

备选模型、选择理由、每个 bot 调用的生成模型，见 `Bot分工与技能说明.md` §1.4。图片能否经 NexorAI 和 nex_bot 正常传进模型，放进统一实验验证。

6. 两把密钥已经存进这台 Mac 的钥匙串（服务名 `NEXORAI_API_KEY`、`MINIMAX_H3_API_KEY`），由 `gen` 在调用时读取。bot 不直接接触密钥，密钥也**不写进 SOUL、SKILL 或作品目录**。

### 9.2 技能导入

nex_bot 导入技能时**只保留 `SKILL.md`，会跳过 `scripts/`、`references/` 等附带文件**（`server/skills.ts` 的安全设计）。所以规范和脚本都放在工具目录里，bot 通过文件工具按需读取，每个 bot 只导入自己岗位的 `SKILL.md`。每份岗位 SKILL 的第一行都要求先读 `OVERRIDES.md`。

**每个 bot 的必读清单统一以 `Bot分工与技能说明.md` 为准**，本文不再重复列出（D1）。

### 9.3 审批级别与预算

- **总导演设为"Approve for me"，不要设成完全权限**。
- **注意（H1 修正）**：nex_bot 会把 Chief 的审批级别带给它委派出去的工作，而且只升不降（`docs/approval-levels.md`）。所以美术、摄影即使设成"Ask for approval"，被总导演派活时**实际也是"Approve for me"**，付费提交**不一定会弹审批卡片**。因此：
  - 花钱的保护**完全依赖提交脚本里的预算检查**（已在 `h3_task.py` 实现；NexorAI 生图脚本在 P0 实现）；
  - 你直接和美术、摄影对话时，它们仍然按自己的"Ask for approval"弹卡片。
- 编剧、剪辑设为"Auto-accept edits"。它们经常要运行命令，你直接和它们对话时，命令仍会弹审批（M4）；被总导演派活时会提升到"Approve for me"。
- **预算按批次给额度**（已确认）。`approvals/budget.json` 的示例：

```json
[{"batch": "EP001-参考图", "kind": "image", "limit": 20, "used": 0, "approved_by": "user", "approved_at": "..."},
 {"batch": "EP001-试生成", "kind": "video", "limit": 400, "used": 0, "unit": "points", "approved_by": "user", "approved_at": "..."}]
```

  - 总导演根据估算向你申请一个批次的额度，你在对话里批准后，由总导演写入。
  - `gen submit` 在额度内自动提交，超出就拒绝。
  - 失败、取消、被拦截的任务，按平台规则释放预占的额度。

## 11. 画布

### 11.1 定位

v1 是**只在本机访问的只读监控面板**（只监听 `localhost`，不做登录）。直接读作品目录，不依赖 nex_bot 的接口。在手机上可以通过 NexBot 看总导演的汇报。

### 11.2 视图

0. **作品列表（首页）**：读 `作品清单.json` 和全局账本，列出每部作品的状态、当前阶段、在等谁、已花积分，以及账户余额；点进去看下面的单部作品视图。
1. **流水线总览**：7 个阶段做成横向节点，显示完成度、负责的 bot、是否卡在审核点。
2. **资产墙**：角色、场景、道具卡片，含缩略图、状态，以及形态之间的关系连线。
3. **Clip 依赖图**：每集一行，clip 是节点，`continue_from` 是连线，颜色表示状态；点开可以对比试生成和定稿的视频，也能看提示词和尾帧。

5. **事件时间线**：合并所有 `logs/*.jsonl`。

### 11.3 技术方案

- 前端：Vite + React + React Flow。
- 后端：一个很薄的本地服务（Node 或 Python），负责读取作品目录、监听文件变化并通过 WebSocket 推送；只允许访问 `~/漫剧/作品/`。
- 单价从 `tools/gen/profiles/*.json` 读取，花费从任务记录读取。

### 11.4 后续版本

v2 在画布上加"重做 / 通过"之类的按钮，点击后给总导演发消息，而不是让画布直接改文件。这需要先调研 nex_bot 有没有供外部程序发消息的接口，或者用 webhook 实现。

## 12. 风险

| 风险 | 对策 |
|---|---|
| 交接次数多，token 成本上升 | 5 个 bot；消息只传文件路径；每个 bot 只读本岗位的规范 |
| 多个 bot 同时写文件 | 单写者原则 + `pipeline_state.py` 加锁 |
| bot 自主推进，确定性不如写死的代码 | 每个阶段都跑 `validate_project.py`；设人工审核点 |
| 意外花费 | 批次额度 + 适配层的硬性检查 + 默认并发为 1 |
| 结果不明时重复提交 | 本地任务记录 + H3 的 `Idempotency-Key`；先查询，不自动重提 |
| 试生成和定稿画面不一致 | 定稿也要审核；允许"试生成直接作为定稿"（§8.1） |
| 原文里夹带指令 | 原文只当数据；同伴的消息不可信 |
| 密钥泄露 | 只存在钥匙串，由 gen 读取；`request.json` 和日志里不写密钥、不写 base64 |
| 版权 | 原规范的改名映射不能代替改编授权；公开发布前需要确认授权 |
