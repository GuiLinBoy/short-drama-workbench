# 作品数据规范 v2

- 日期：2026-11-03（P0 第 1 组）
- 基于：原技能包 `skill/references/project-schema.md`（v1）。v1 的字段、编号规则、四种状态、路径规则**全部沿用**；本文只写新增和改动的地方。
- 依据：设计文档 §5.2–§5.3、§6.1、§6.3、§8.5、§8.6；`Bot分工与技能说明.md` 各 bot 的"写的文件"。
- **本文是 `tools/pipeline_state.py` 和 `tools/validate_project.py` 的唯一依据**（审查报告 H8）。两个脚本里的字段归属表和校验规则要和本文一致；改规则先改本文。

## 0. 总规则

- 所有路径都**相对于作品目录**，不能是绝对路径，不能跑出作品目录（沿用 v1）。
- 状态只有四个：`planned` / `generated` / `approved` / `failed`（沿用 v1，不新增）。
- `assets.json`、`clips.json`、`voices.json` 只能通过 `pipeline_state.py` 修改（带锁、按角色限制字段、写前备份、记日志）。
- **创建者填初值，之后归属者修改**：例如编剧新建片段时要填 `video` 的计划路径（v1 必填），之后 `video` 只能由摄影改。
- `approved` 只能由总导演写（资产、片段定稿、片段试生成、音色模板都一样）。
- 校验分**错误**（不通过）和**提醒**（通过，但要在回报里说明）。

## 1. `project.json`（总导演写）

新作品登记自动安装指向共享规范的 `AGENTS.md`；直接建立配置时运行 `tools/project_rules.py --project <作品目录> --install`。规范入口不复制角色、音色、预算、审核或历史暂停状态。新项目配置使用下列现行默认值，不把假素材样例或历史验收配方当生产模板。

```json
{
  "schema_version": 2,
  "title": "样例作品",
  "mode": "series",
  "genre": "3d-guoman",
  "ratio": "9:16",
  "character_sheet_ratio": "16:9",
  "target_duration": 60,
  "max_revisions": 2,
  "source": {"path": "原文/样例.txt", "sha256": "…", "range": "第1–3章"},
  "image": {"provider": "nexorai", "model": "grok-imagine-image-quality"},
  "video": {"provider": "minimax-h3", "model": "MiniMax-H3", "draft_resolution": "768P",
            "final_resolution": "768P", "use_context_ir": false, "audio": "generate"},
  "narration": {"provider": "compshare-indextts-2.5", "voice_id": "晚晴", "speed": 1.0},
  "post": {"loudness_lufs": -14, "true_peak_db": -1, "bgm_duck_db": 12, "subtitles": "srt",
           "burn_subtitles": false,
           "aigc_label": {"visible": true, "metadata": true, "text": "本片含 AI 生成内容", "badge": "AI 生成", "badge_position": "top-right"}},
  "publish": false
}
```

| 字段 | 必填 | 取值 / 说明 |
|---|---|---|
| `schema_version` | 是 | `2`。没有这个字段或为 `1` 的是旧作品，校验只做 v1 检查并提醒升级 |
| `title` | 是 | 作品名，和目录名一致 |
| `mode` | 是 | `series`（长篇，默认）/ `short`（短片，§8.6） |
| `genre` | 是 | `genres/<genre>.md` 必须存在：`3d-guoman` / `live-action` / `urban` |
| `ratio` | 是 | `21:9` `16:9` `4:3` `1:1` `3:4` `9:16`（H3 支持的比例，不用 `adaptive`） |
| `character_sheet_ratio` | 否 | 三视图比例，默认 `16:9` |
| `target_duration` | 否 | 长篇是每集秒数，短片是整片秒数 |
| `max_revisions` | 否 | 默认 2 |
| `source` | 否 | 原文路径、哈希、选定范围（v1 要求"另记录"，这里给出固定位置） |
| `image` | 是 | `provider` 目前只有 `nexorai`；`model` 按题材配置的优先级 |
| `video` | 是 | `provider` 目前只有 `minimax-h3`；`model` 为 `MiniMax-H3`；`draft_resolution`/`final_resolution` 取 `480P` `768P` `1080P`；`audio` 为 `generate` 或 `mute` |
| `narration` | 否 | 没有旁白的作品可以不写；写了就要有 `provider`、`voice_id` |
| `post` | 是 | 响度、峰值、配乐压低量；`subtitles` 为 `srt` 或 `none`；`burn_subtitles` 短片默认 `true`、长篇默认 `false` |
| `post.aigc_label` | 是 | `visible`、`metadata` 两个开关；发布用途（含 delivery_intent）时两个都必须是 `true`（§8.8） |
| `publish` | 否 | 旧版发布标记；为 true 或 delivery_intent 指定发布时都启动发布检查 |
| `delivery_intent` | 否 | `{purpose: preview/public-release, platform, use, basis}`；记录用户已知目标和用途，不代表取得授权或已发布 |
| `specification_status` | 否 | 初始化可为 proposal_pending_user_review；生产前须依据已批准材料同步，不能用待审占位进入生产 |

v1 的 `image_model`、`video_model`、`poll_interval`、`poll_window`、`max_concurrency` **不再使用**（OVERRIDES §3）；出现时校验给提醒。

## 2. `assets.json`

v1 的必填字段不变：`id,type,name,detail,prompt,image,status`。新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `sheet` | 路径，可选 | 角色三视图设定稿，只给人看，不传给 H3（Bot分工 §2.3）。只用于 `character` |
| `sheet_prompt` | 路径，可选 | 三视图的提示词文件（`….sheet.prompt.txt`） |
| `voice` | 字符串，可选 | 角色卡里的**音色描述句**（当前按用户要求用中文，包含年龄、性别、音高、音色、语速），编剧写，所有片段原样复用。历史英文记录保留，只用于 `character` |

- 角色只有 `image`（视频参考图）通过才能用于提交；`sheet` 是可选的，但**写了 `sheet` 的角色要两张都通过才能标 `approved`**，所以 `approved` 的角色如果有 `sheet`，文件必须存在。
- **场景状态**（白天/夜晚、完好/损毁等，审查报告 M7，按原技能包 `asset-management.md`）：临时状态写在片段的镜头描述里，不另建资产；会在多个片段里稳定出现的新状态，另建一个场景编号（例如 `S00002`），`source_asset_id` 指向原场景、`relation` 写 `derived`。

## 3. `clips.json`

v1 的必填字段不变：`id,episode,duration,assets,prompt,video,continue_from,status`。改动和新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `duration` | 整数 | **4–15 的整数**（OVERRIDES §3）。v1 允许小数，v2 不允许 |
| `status`、`video` | | **只表示定稿**（768P）。合成只看这两个字段 |
| `draft` | 对象，可选 | 试生成：`{"video": 路径, "status": 四种状态, "task_dir": 路径, "ending_frame": 路径}` |
| `needs_draft` | 布尔，可选 | 是否需要额外试生成，长短片均按当前制作计划和批准范围；不强制每段做两次 |
| `voice_anchor` | 数组，可选 | 这个片段里有**定音台词**的角色编号，例如 `["C00001"]`（§8.5.1） |
| `narration` | 数组，可选 | 旁白，见下 |
| `task_dir`、`ending_frame` | 路径，可选 | 定稿的任务目录和尾帧（v1 已有）。**摄影提交成功后立即写 `task_dir`**（试生成写 `draft.task_dir`），画布靠它把"planned + 有未结束任务"显示为生成中 |
| `final_from_draft` | 布尔，可选 | 你决定"直接用试生成作为定稿"时由总导演写 `true`（设计文档 §8.1）。这时 `video` 指向试生成文件（不复制），`draft.status` 必须已是 `approved`；合成报告列出实际采用尺寸和来源，不假定试片必为 480P |
| `fingerprint`、`draft.fingerprint` | 对象，系统写 | 见 §7.5，任何角色都不能手动改 |

尾帧文件名：试生成的尾帧存 `单集制作/EPxxx/尾帧/ClipNNNNN-draft.png`，定稿的存 `单集制作/EPxxx/尾帧/ClipNNNNN.png`（分别记在 `draft.ending_frame` 和 `ending_frame`）。定稿承接必须用上一段**定稿**的尾帧（§8.1）。

`narration` 每一项：

```json
{"id": "Clip00003-1", "start": 2, "reserved": 4, "text": "那一夜，山门外的雪下得很大。",
 "audio": "单集制作/EP001/旁白/Clip00003-1.wav", "narration_duration": 3.6}
```

- `id`：`Clip<五位>-<序号>`，和片段编号一致；
- `start`：从片段第几秒开始；`reserved`：编剧预留的秒数（约每秒 4 字）；`start + reserved` 不能超过 `duration`；
- `audio`、`narration_duration`：剪辑配好旁白后写入。**实际时长超过预留**就提醒（由编剧调整片段），**超出 1 秒以上**要总导演告诉你（§8.5.5）。

试生成和定稿的关系（§6.1）：

```json
{"id": "EP001/Clip00002", "status": "planned", "video": "单集制作/EP001/视频_Clip00002.mp4",
 "draft": {"video": "单集制作/EP001/试生成/视频_Clip00002.mp4", "status": "approved",
           "task_dir": "tasks/EP001-Clip00002-draft/attempt-001"}}
```

## 4. `voices.json`（音色模板登记，§8.5.1）

所有作品在角色首次开口视频通过后的同一轮提取、核对、登记并提交声音画布项；样本通过后同轮同步采用。收尾状态由实际视频审核、文件 SHA、登记和音频审核共同计算，不能只检查文件存在或视频 `approved`。`tools/voice_lifecycle.py` 提供只读检查；后续同角色视频须实际引用已通过音色。详见 [执行要求](tools/VOICE_CLOSEOUT.md)。

顶层为数组：

```json
[{"character": "C00001", "file": "音色/C00001.wav", "source_clip": "EP001/Clip00005", "start": 3.2, "end": 7.2,
  "text": "哼，你以为我会怕你？", "status": "generated", "forms": ["C00001-A", "C00001-B"]}]
```

- `character`：角色编号 `C00001`；只有年龄、物种这类会改变声音的形态，才写形态编号（`C00001-C`）另起一条；同一个 `character` 只能有一条；
- `forms`：共用这个模板的形态，必须是 `assets.json` 里这个角色的形态；
- `source_clip`：必须是 `clips.json` 里的片段；
- `start`、`end`：模板文件在源片段里的起止秒数，**包含前后各 0.2 秒的留白**，也就是 `end - start` 等于模板文件的实际时长；
- `end - start`：按视频模型的建议值，H3 是 3–5 秒（建议约 4 秒，含留白不超过 5 秒）。不在这个范围就提醒；
- `status`：摄影截取后写 `generated`；你确认后总导演写 `approved`。`approved` 的模板文件必须存在。
- 首次截取可用 `align.py cut-voice --start … --end … --out 音色/C00001.wav`，文件验证通过后再经 `pipeline_state.py` 登记 `generated`；截取工具不写 voices.json，不覆盖已存在模板，输出须在作品内。

## 5. `approvals/budget.json`（批次额度）

格式由 `h3_task.py` 定义，顶层为数组：

```json
[{"batch": "EP001-试生成", "kind": "video", "unit": "points", "limit": 400, "used": 0}]
```

- `limit` 由总导演写（你批准后）；`used` **只由提交脚本写**。不通过 `pipeline_state.py`。
- **只认作品自己的预算文件**：`h3_task.py` 要求 `--task-dir` 是 `<作品>/tasks/<任务名>/attempt-NNN`，`--budget` 必须正好是这个作品的 `approvals/budget.json`，放在别处的预算文件一律拒绝。积分**只按每部作品的批次额度控制**，不设全局积分上限（2026-11-03 你决定）；提交前查账户余额和全局并发（全局设置.json / 全局账本.jsonl，见 §9）。
- `kind`：`video`（单位 `points`）、`image`（单位 `images`）、`speech`（单位 `points`）；
- 校验：批次名不能重复；`limit`、`used` 是非负数；`used` 不超过 `limit`。

## 6. 日志

- `logs/<bot名>.jsonl`：各 bot 只追加自己的事件 `{"time","bot","stage","target","event","files","note"}`（§6.2）。
- `logs/state-changes.jsonl`：`pipeline_state.py` 每次修改追加一行 `{"time","role","file","target","action","changes"}`，`changes` 是 `{字段: [旧值, 新值]}`。
- `.backup/`：`pipeline_state.py` 每次写入前把旧文件复制一份（`assets.json.20261103T101500123456`），每个文件保留最近 50 份。
- 写入安全（`pipeline_state.py`）：
  - 写入前检查类型和路径：路径必须在作品目录内，`duration` 必须是 4–15 的整数，时间是非负数字，`needs_draft` 是布尔，`assets` 等是数组；
  - 写入没成功就删掉这次的备份；日志写不进去就撤销这次修改，保证每次修改都有日志；
  - Windows 上目标文件正被别的程序读取时，替换会自动重试最多 10 秒；等锁最多 60 秒，超时报错，不会无限等。

### 7.4 状态转换

"产出者"指：资产是美术，片段定稿、片段试生成和音色模板是摄影。

| 从 → 到 | 谁能做 | 场景 |
|---|---|---|
| `planned` / `failed` → `generated` | 产出者 | 生成完成并自检通过；返工后重新生成 |
| `planned` / `generated` → `failed` | 产出者 | 明确失败、被拦截、自检不通过 |
| `generated` → `approved` | **只有总导演** | 你在审核点确认后 |
| 任何状态 → `failed` / `planned` | 总导演 | 质检或你驳回；需要从头重做（例如改了风格要重审） |

- 同一个状态"改成自己"不算转换，不记日志。
- 片段在 `status` 变成 `approved` 之前，如果是长篇模式，`draft.status` 应当已经是 `approved`（提醒，不报错：你可能决定"直接用试生成作为定稿"或跳过试生成）。
- `draft` 整个清空（`{"draft": null}`）只能由总导演做，例如决定这一段跳过试生成。
- `final_from_draft` 只能由总导演写。

### 7.5 系统自动规则（`pipeline_state.py` 自动执行，日志里记在 `auto`）

**已通过不等于永远通过**：内容变了就自动降级，必须重新审或重新生成。

| 谁改了什么 | 自动结果 |
|---|---|
| 美术改了已通过资产的 `prompt` `image` `sheet` `sheet_prompt` | 资产 `status` 退回 `generated`，要总导演重新审 |
| 编剧改了资产的 `detail` `visual_summary` `design_additions`（资产是 `generated` 或 `approved`） | 资产 `status` 退回 `planned`，要美术重新出图或确认后再标 `generated` |
| 摄影改了已通过片段的 `video` `ending_frame`（或试生成的 `draft.video` `draft.ending_frame`） | 对应的 `status`（或 `draft.status`）退回 `generated` |
| 编剧改了片段的 `duration` `assets` `prompt` `continue_from` `shots`（片段是 `generated` 或 `approved`） | `status` 和 `draft.status` 都退回 `planned`，要重新生成 |
| 摄影改了已通过音色模板的 `file` `start` `end` `source_clip` | 模板 `status` 退回 `generated` |
| 编剧改了某条旁白的 `text` | 这一条的 `audio` 和 `narration_duration` 自动清空，由剪辑重新配音 |

如果同一条命令里已经显式改了这个状态，就按显式改的来（照常受 §7.4 限制）。

**文件指纹**：bot 常常直接改提示词文件、或者用同一个文件名覆盖图片和视频，这些都不经过 `pipeline_state.py`。所以：

- 状态变成 `generated` 时，`pipeline_state.py` 自动记录产出文件的 sha256：资产记 `image`、`sheet`；片段定稿记 `video`、`prompt`；试生成记 `draft.video`；音色模板记 `file`。文件不存在或为空就**拒绝**标 `generated`；
- 总导演标 `approved` 前，核对这些文件和指纹一致；不一致（生成之后又被改过）就拒绝，要产出者重新确认后再标 `generated`；
- `tools/validate_project.py` 也会检查：`generated`/`approved` 的条目，文件和指纹不一致就报错；
- 状态退回 `planned` 时清掉指纹。

### 7.6 用户明确禁用额外清单备份

`project.json` 可配置 `"storage": {"manifest_backups": false}`，必须为布尔值。仅对此作品跳过新建 `.backup` 和旧备份清理，旧文件全部保留；原子写、角色权限、锁、审计日志、指纹与审批失效规则仍执行。日志失败时从本次操作内存中的原始字节回滚，不依赖持久备份。其他作品未设置时保持原行为，本次验收不修改既有作品配置。

## 9. 全局文件（`漫剧\` 根目录，所有作品共用）

生图（第 2 组）和 H3（第 3 组）都用这一节的全局文件。

### 9.1 `全局设置.json`（只有你能改，脚本只读）

```json
{"h3": {"max_running_tasks": 3},
 "nexorai": {"images_cap_per_day": 50, "images_per_batch": 12, "max_running": 2},
 "active_projects_max": 3}
```

- 不存在时，生图或 H3 脚本第一次运行会按上面的保守默认值生成；之后由你修改。
- **不设全局积分上限**：积分只按每部作品的批次额度控制（2026-11-03 你决定），全局上限就是账户余额（提交前查余额，余额接口失败只警告不拦提交——平台会拒绝余额不足的提交并退回）。
- `h3.max_running_tasks`：所有作品合计同时跑的 H3 任务数上限（状态为 submitting/submitted/pending/unknown 的都算占用）；
- `images_cap_per_day`：所有作品合计每天最多出几张图（按本机日期，按全局账本统计）；
- `images_per_batch`：一个生图批次的 `limit` 不能超过它，超过就拒绝提交，请总导演拆成更小的批次；
- `nexorai.max_running`：所有作品合计同时在等的生图请求数上限（同步接口，state 停在 submitting 就算在等）。
- 并发满时不报错、不扣额度、退出码 4（排队）：这个 attempt 原样保留，之后可以直接再提交。锁用专用的 `全局设置.lock` / `全局账本.lock` 文件（不锁 `全局设置.json` 本身），检查、占位、扣额度、写状态、记账在同一把锁里完成，两个 bot 同时提交不会都通过并发检查。

### 9.2 `全局账本.jsonl`（只由提交脚本追加）

每行一条。生图（`"provider": "nexorai"`，按张数记账）：

```json
{"time": "2026-11-03T12:00:00+08:00", "provider": "nexorai", "event": "charge", "date": "2026-11-03",
 "project": "样例作品", "batch": "EP001-参考图", "task_dir": "…/tasks/C00001-A-image/attempt-001", "images": 1}
```

H3（`"provider_event": "h3"`，按积分记账）：

```json
{"time": "2026-11-05T12:00:00+08:00", "event": "charge", "provider_event": "h3", "project": "样例作品",
 "batch": "EP001-试生成", "task_dir": "…/tasks/EP001-Clip00001-draft/attempt-001", "points": 30,
 "available_points": 4544.3}
```

- 生图 `event`：`charge`（提交前扣）、`refund`（明确失败退回，`date` 写原来扣的那天）、`quota_exhausted`（平台说额度用完，当天暂停生图）、`resume`（你确认恢复）；
- 生图"当天已出张数" = 当天 `charge` 减去 `refund`；当天最后一条暂停相关记录是 `quota_exhausted` 时，所有生图提交都拒绝，直到第二天或有 `resume`。
- H3 `event`：`charge`（提交前按预估扣，带 `points` 和提交时的 `available_points`）、`settle`（成功后按平台实际用量结算，带 `estimated_points`/`actual_points`/`adjusted`，`adjusted` 是退回批次的差额）、`refund`（明确拒绝/失败/拦截/取消时退回预估）。
- H3 结算语义：批次先按预估扣，成功结算时**把多扣的退回**（实际比预估少，`adjusted` 为正）；实际比预估多时补扣。批次 `used` 最终等于实际用量。

## 10. 2026-11-06 第一批修复补充（本地实现，真实接口尚待验收）

本节澄清计费/并发/旁白写回的实现契约，不构成真实消费批准。

- 三个生成入口共用 `tools/generation_runtime.py`。全局占位锁统一为 `全局设置.lock`，账本锁统一为 `全局账本.lock`；同一 attempt 的提交/查询/下载还需持有 `.attempt.lock`。锁顺序为 attempt → 全局占位 → 预算 → 账本；共享清单锁在计费锁释放后获取。
- H3 与 IndexTTS 双向共用名额池；生图单独计数，但使用统一的全局占位锁。submitting/submitted/pending/queued/generating/running/unknown 均算占用。无法解析的 state 或无 state 的持久提交标记会阻止新提交，须核对，不能静默跳过；60 分钟不自动退款、释放或重新提交。
- 幂等键包含作品路径与完整 attempt 路径。已有 attempt 重试沿用保存的键，不能搬目录后重新计算旧键再提交。NexorAI 同步生图没有已验证的幂等重放能力，仍不自动重试。
- `approvals/budget.json` 保留原有数组与批次字段。新增可选 `_operations`（固定操作编号 → 已应用差额）与 `pending_settlements`（操作编号 → 未能纳入批准额度的实际费用）；由提交/结算工具管理，不能人工清空。
- attempt 新增 `accounting-charge/settle/refund.json`，先保存意图，再把预算变化与去重凭据原子写入同一文件，然后按 operation_id 去重追加全局账本并保存任务状态。中断后进入同一 attempt 的提交/查询/fetch 会先恢复未完成的计费操作。此为本地进程中断恢复机制，不是跨平台收费的分布式事务或断电耐久承诺。
- 查询 401/404/429/500、超时、格式不明都不能证明平台未消费，不退款。任务失败/取消需要 `point_status=released` 才退款；仅有失败状态但无释放证据时记录 refund_pending。成功结算与媒体下载分开，下载失败不撤回或重做结算。
- 实际费用超过 limit 时，不自动增加 limit，也不抹去差额：state/计费意图保存实际费用，批次记录 pending_settlements，阻止该批次新提交。用户另行批准调整额度后，通过原 attempt 的 query 恢复结算。used 在完成结算前仍保留原预占，不能单看 used 判断全部实际支出。
- 新增账本事件有唯一 operation_id；旧事件原样保留，不按新格式重算或清洗。发现账本损坏/不完整尾行会停止追加，要求核对。
- 旁白 prepare 完全离线。本地音色目录默认 `approvals/tts-catalog.json`，格式 `{"voices":[{"name":"音色名","voice_id":"已核对的ID"}],"unit_price":0.01}`；这里的数字只是本地估价，可用 --unit-price 显式指定，不代表现时报价。目录重名或名称不存在则拒绝准备，不隐式取密钥或联网。pricing/voices 是显式在线只读命令，本轮未调用。
- 旁白请求新增 source_fingerprint，绑定作品、clip/entry、文本及旁白配置。提交前核对；下载后经 pipeline_state 在同一清单锁内再次核对并写回。旧请求缺少指纹不能直接作为新提交使用；旧任务结果没有来源证据时不能自动挂接。
- 视频/旁白输出必须在当前作品内，已有输出不覆盖；以同卷原子 no-clobber 发布防止不同 attempt 同时覆盖目标。媒体下载/清单挂接失败可保留结果供人工核对，不重发生成。
- pipeline_state 原有内置 .backup 政策本批未修改；所有测试在隔离根运行，未对真实作品新增备份。字幕、混音、经验工具、第 7/8 组与真实 bot 验收仍是后续事项。
